## Known conflict and how it is resolved (tell the user in the final report)

A 1366x768 laptop usually runs at 125% or 150% DPI: logical screen 1093x614 or 911x512. A hard 1280x720 logical minimum cannot fit those screens (the window would hang off-screen, the status bar and command line land under the taskbar).
A second, smaller problem exists even at 100%: the 720 pt minimum is the CLIENT height. With the taskbar (~40-48) and the title bar (~31) the client area of a maximized window on 1366x768 is about 1366x690, so 1280x720 does not fit there either.

Chosen default (user-approved shape, one refinement): effective minimum = per axis `min(1280x720, usable area in logical points)`, never below the planner floor 800x400.
- `usable area = monitor_size_logical - (16, 80)`: 16 pt window frame width, 80 pt = 48 taskbar + 32 title bar. These are conservative constants (named, in one place), not measured. The refinement versus the user's wording: the reserve includes the title bar, not only the taskbar. If the user prefers taskbar-only, change one constant (`SHELL_RESERVE_PT`).
- `monitor_size` unknown (`None`), non-finite or not positive: plain 1280x720 (safe fallback, never zero).
- Results (default constants): 1920x1080 or larger -> 1280x720. 1366x768 @100% -> 1280x688. @125% (1092.8x614.4) -> 1076.8x534.4. @150% (910.7x512) -> 894.7x432. Tiny monitors -> floor 800x400.
- Builder: the first frame cannot know the monitor, and a 1280x720 builder minimum on a 150% laptop would be 1920x1080 physical on a 1366x768 screen. So the builder gets the safe floor (800x400) and `MatrixApp::show` sends `ViewportCommand::MinInnerSize(effective)` on frame 0 and whenever the effective value changes (monitor or DPI change). `AppConfig.min_window` becomes the nominal supported minimum 1280x720 (used by `validate`). Tests prove frame 0 emits the command; the real-exe matrix proves the receipt reports it.
- Risk that cannot be proven here: a maximized start on a real 1366x768 @125/150% device. Put it in the human checklist. If it overflows, the fallback is a one-time `Maximized(false)` then `Maximized(true)` nudge after the first cap.

## Design decisions

- D1 (floor and error path). Planner floor `PLAN_FLOOR_WINDOW = 800x400`, independent of the left rail. It is below every size the window level can produce (lowest cap on a 1366x768 @150% screen is 895x432). Below it: `WindowTooSmall`, `Layout:` status error, last good plan kept (behaviour unchanged, numbers only). The documented supported minimum is `SUPPORTED_MIN_WINDOW = 1280x720`; the floor exists only so the capped case still plans. Hiding the left rail no longer lowers the minimum (one test and two fixture cases change, listed below).
- D2 (right-dock threshold = 1200 logical). Why: at the default rails (left 300, right 300, gap 2) the viewport width is `(W - 602) / 2`. A viewport needs about 300 pt to stay useful; the old 915 pt rule gave viewports of roughly 160 pt (at 915, estimated from the formula, to be confirmed by the evidence table) up to 299 pt (at 1199). 1200 gives 299 pt. It also makes the three 1366x768 modes behave sensibly: 100% (1366) shows the dock with 382 pt viewports; 125% (1093) and 150% (911) yield the dock and keep 395 pt and 305 pt viewports. It keeps the nominal minimum 1280 above the threshold (dock shows at 1280x720 with 339 pt viewports), so existing 1280x900 tests keep their dock. A derived rule (dock only if viewports stay above 300 for any rail width) was rejected: it changes `DockLayout::resolve` semantics and the widest rails (420+420) can still squeeze viewports; record it as a follow-up for L3-003 (live resize). Change: `NARROW_WINDOW_WIDTH` 900 -> 1200 in `dock_layout.rs` line 48 (doc comment updated). Consequence: `YieldReason::NotEnoughRoom` and `RegionNote::LeftRailShrunk` become unreachable from `compute_regions` (1200 > 420 + 420 + 320 and 800 > 420 + 320). Keep the enum variants (public, serde, fixtures); add a test asserting those two inequalities so a later constant change cannot silently reopen the gap; say it in the doc.
- D3 (pure sizing function). `startup.rs`: `pub const SHELL_RESERVE_PT: [f32; 2] = [16., 80.]` and `pub fn effective_min_size(monitor_logical: Option<[f32; 2]>) -> [f32; 2]` (nominal and floor imported from `workbench_regions`). Per axis: unknown or non-finite or `<= 0` monitor -> nominal; else `max(floor, min(nominal, monitor - reserve))`. No panics, no NaN, no zero.
- D4 (audit simulation). New audit-only `OM9_UI_AUDIT_MONITOR=WxH` (physical px of a simulated monitor, same parser style as `parse_window_size`; read only when an audit directory is given; bad value = visible startup failure like `OM9_UI_AUDIT_ZOOM`). With it, the governor uses `monitor_px / ctx.pixels_per_point()` instead of `viewport().monitor_size`. Without it, a normal start never reads the variable. Needed so the capped high-DPI case can be shown in a real window on the 2560x1440 test display. Labelled SIMULATED.
- D5 (no change). The 311 px command-panel mismatch is below the new floor (floor height 400), recorded as out of supported range; the Line-save archive defect in `om9-archive` stays unfixed and listed.
