No change to order logic.

Root cause of "Layers on the right": `ui.rs::launch_with` (search `OM9_UI_AUDIT_RIGHT_DOCK`) calls `app.dock_menu_section(SectionId::Layers, DockSide::Right)`; the validator sets that env at every case; tests use Layers as the right-dock fixture (`shell_docking.rs` ~254, `status_bar_overlap.rs` ~31, `workbench_regions_sizes.rs` ~83/365/415, `workbench_regions.rs` ~374/406/433/486, `dock_layout.rs` unit tests ~959/979). `workbench_regions.rs` unit tests and `implementation/fixtures/.../positive.json|negative.json` already use `main-menu`, not Layers: leave them.
3. Spurious "Error: unsupported unknown/unavailable command" (lap125/lap150 receipts, `cmd` field): the scripted `Text("Line")` of audit step 0 is lost, so step 1 `Enter` hits an empty draft ("missing previous command"), then `0,0,0` is submitted as a command, and later drafts concatenate (`0,0,012,6,0UndoRedoLine2,2,0`). Those two cases also carry a `Layout: right dock hidden: window is narrow` notice, and min-1280x720 (no notice) works. The script lives in `ui.rs::raw_input_hook` (the `match step` block, steps 0..15) and fires from `passes >= 2` without checking that the CMD field has focus. It is a script/focus-timing problem, not a layout error (`regions.error` is null). Exact trigger is NOT yet proven: item 1 measures it before the fix.
4. Icons: `chrome.rs::icon()` allocates a fixed `Vec2::splat(22.)` and paints the authored SVG via `self.icons.paint(ui, rect.shrink(2.), name)`. `icon()` is shared by the sidebar sections (`icon_row`, `feature_icon`, builder parameters, `section_bar_controls`) AND by the toolbar (`toolbars_ui`). Rows already use `ui.horizontal_wrapped`, so wrapping exists.
5. Width: `LEFT_RAIL_MIN/MAX/DEFAULT = 240/420/300`, `RIGHT_DOCK_MAX = 420`. `ui.rs` uses `egui::Panel::left("matrix-sidebar").default_size(regions.left_rail).min_size(..).max_size(..).resizable(true).frame(inner_margin 2)` and calls `sync_panel_size(PanelId::LeftRail, ui.max_rect().width())`: that is the INNER width after margins (receipts: 295 at 1280 and 1600), while plans and tests say 300. The planner (`workbench_regions.rs`, `DockLayout::resolve`) works with the stored number as if it were the outer width.
6. Invariants that bound the rail maximum: compile-time `PLAN_FLOOR_WINDOW.width (800) >= LEFT_RAIL_MAX + CANVAS_MIN_WIDTH (320)` => MAX <= 480; compile-time `NARROW_WINDOW_WIDTH (1200) > LEFT_RAIL_MAX + RIGHT_DOCK_MAX (420) + CANVAS_MIN_WIDTH` => with the strict `>` MAX <= 459; with `>=` MAX <= 460 (and `resolve()` tests `left + right + CANVAS_MIN_WIDTH > width`, which is false at width 1200 when the sum is exactly 1200, so `NotEnoughRoom` stays unreachable).
7. The right dock is hidden by default (`PanelId::RightDock` visible=false; `Regions.right_dock_visible` needs a right-docked visible section AND width >= 1200). BUT `chrome.rs::settle_section_drag` only docks right when the pointer is inside `self.right_dock_rect`, and that rect is `None` while the dock is hidden. So today a user cannot drag a panel from the left column into a hidden right dock (the only paths are the floating-menu "dock right" button). The user's decision (b) "appears only when the user drags a panel there" therefore needs a minimal drop target (item 5).
8. Current evidence for sizes: sidebar height 695 px at 1280x720 (receipt `sidebar_px` `[2,23,295,695]`); Layers title started near y=338 at 1600x1000 (about 315 px below the sidebar top) in the old screenshot, so it likely fits without scrolling; this was read by eye and is re-measured in item 1.

## Decisions (each with the reason; do not re-open)

D1. Neutral right-dock fixture = `SectionId::Snaps`, exported as `pub const RIGHT_DOCK_FIXTURE: SectionId = SectionId::Snaps;` in `dock_layout.rs`. One source of truth for the audit hook, all unit tests and `tests/common/mod.rs`. Reason: Snaps has no builder or layers content, keeps its controls on the closed bar, and `shell_docking.rs` already uses it. Layers is never docked right by any audit, fixture or test (a user doing it by hand is still allowed by the product).
D2. Audit layout modes: env `OM9_UI_AUDIT_LAYOUT_MODE` = `default` (also when unset: nothing docked right, used for every Matrix-parity screenshot) | `user-docked-right` (docks `RIGHT_DOCK_FIXTURE` right; labelled "user-initiated OM9-extension layout, not a Matrix9 parity capture"). Any other value is a visible startup failure (never ignored). The old `OM9_UI_AUDIT_RIGHT_DOCK` is REMOVED; if it is still set the launch fails with "OM9_UI_AUDIT_RIGHT_DOCK was replaced by OM9_UI_AUDIT_LAYOUT_MODE=user-docked-right" so a stale script cannot silently run the wrong mode. The receipt records `audit.layout_mode` and `audit.mode_label`.
D3. 295 vs 300: 300 is the OUTER panel width (frame margins included). It is what the manual and the user mean, what `LEFT_RAIL_DEFAULT`, `default_size`, `PanelState.size`, `resolve()` and the planner use. The INNER content width is outer minus the frame chrome (2 px margin on each side, plus whatever egui adds; measured in item 1 and named `LEFT_RAIL_CHROME_PX`). The code stores the outer width: capture the panel rect from the `Panel::show` return value (`InnerResponse.response.rect.width()`), not `ui.max_rect().width()`. Receipt and tests state both numbers (`left_rail_outer_px`, `left_rail_inner_px`). If the measured outer width is not 300 +-0.5 at default, fix the `default_size`/sync until it is, and record the number in the doc. No schema bump: the stored value is still a clamped width; an old saved 295 is simply read as outer 295 (within 240..460).
D4. Rail maximum: `LEFT_RAIL_MAX` 420 -> 460. 460 is the largest value that keeps BOTH the 800 px plan-floor guarantee (800 >= 460 + 320) and the "dead notes stay unreachable" invariant (1200 >= 460 + 420 + 320, equality), so the 1200 pt right-dock threshold and the 320 pt canvas minimum stay intact. The compile-time assertion in `workbench_regions.rs` changes from `>` to `>=` (exactly equal at 1200; `resolve()` uses `>` so nothing yields at 1200). 480 would make `NotEnoughRoom` reachable between 1200 and 1220 and force more assertion rewrites for no reason. The right-dock max stays 420. Justification table is produced by a test (item 6) at 1280x720, 1366x768 at 100/125/150% (windows 1280x688, 1093x585, 911x480 in points) and 1920x1080, each with the rail at 240/300/460 and with/without the user-docked right dock.
D5. Icon rule (monotone, clamped, wrapping keeps rows inside): `rail_icon_edge(outer_width) = clamp(ICON_BASE_EDGE * outer_width / LEFT_RAIL_DEFAULT, ICON_MIN_EDGE, ICON_MAX_EDGE).round()` with `ICON_BASE_EDGE = 22`, `ICON_MIN_EDGE = 18`, `ICON_MAX_EDGE = 34`; non-finite input returns 22. Anchors: 240 -> 18, 300 -> 22, 460 -> 34. The glyph keeps its 2 px inset so the SVG grows with the box. It applies to the sidebar sections only (left column, and the right dock mirror by its own outer width: default 300 -> 22, so nothing changes there by default). The toolbar and every other `icon()` caller stay at 22. Scope: minimal width-driven scaling only. Full sidebar-menu behaviour (text-row clipping, Main Menu tabs, customization) belongs to OM9-L2-03-07 (Matrix left sidebar menus); Layers content stays with OM9-L2-03-14; drag preview with OM9-L3-01-01-003. Record this ownership in the ledger.
D6. No proportional compression: `SectionState.height` stays as is (still unused by rendering; do not wire it). The left stack scrolls/clips when taller than the window.
D7. Hidden-right-dock drop target (minimal, overlay only): while a menu drag is in progress, the right dock is hidden, and the window is >= `NARROW_WINDOW_WIDTH` wide, paint a `RIGHT_DROP_ZONE_WIDTH = 28` pt overlay strip at the right edge of the canvas (foreground layer, no layout reflow) labelled "Drop to dock right"; releasing inside it docks right via the existing `dock_menu_section`. On a window < 1200 pt no zone is shown and a release at the edge does nothing except a status line "Right dock needs a window at least 1200 points wide". Reason: no reflow during the drag, so viewports do not jump. This is the minimum for the user's decision (b); the richer live drag preview stays with L3-003.
