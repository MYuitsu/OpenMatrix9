# Transaction-owned external memory reservations

P0/P3b partial: the coordinator now admits external CPU-cache, upload, kernel and export byte reservations against its existing retained-owner byte limit. Concurrent admission uses one shared lock; optional total/available physical-RAM samples also reserve `max(256 MiB, 10% total)` headroom and conservatively subtract outstanding external reservations. Guards release their charge on drop and the shared reservation account follows controller replacement. Document and Undo remain accounted as owners rather than admitted through these external classes.

The STL background-job foundation now requires an export reservation from the same account as its captured document; wrong-class or foreign-account guards are refused. The guard lives through the worker. This is a real accounting connection for callers that explicitly create such a job, not UI integration and not proof that the caller's requested byte count covers actual scratch or OCCT peak.

Windows with default OCCT/openNURBS, `CARGO_TARGET_DIR=L:/om9-target`, Cargo `-j 2`: nine retained-owner/reservation unit tests passed, including simultaneous competing reservations, headroom refusal, transfer and drop across coordinator replacement. A real transaction test passed where a live reservation caused an oversized edit to be refused while preserving executable Redo. All 29 STL integration tests and 20 file-lifecycle tests passed. Simulated limits and free-RAM values were used; no actual peak RAM or desktop performance was measured.

The interactive UI remains synchronous and does not request an export reservation. The 256 MiB configured aggregate limit remains; there is no complete 60% RAM owner inventory or verified upper bound for kernel allocations, weld/topology maps, CPU/GPU caches or concurrent external processes. Physical RAM samples are point-in-time observations, and the optional sample must be supplied by the caller. Existing conservative accounting can refuse work unnecessarily. New/Open/close cancellation of a running worker and other plan gates remain open. The active OM9 session was not modified.
