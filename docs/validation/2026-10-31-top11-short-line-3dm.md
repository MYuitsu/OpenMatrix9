# Top11 short lines in 3DM

The pinned openNURBS SDK rejects some distinct `ON_LineCurve` endpoints as coincident. Geometry-only 3DM export now represents such a line as a valid non-rational degree-one, two-pole `ON_NurbsCurve` with the original endpoints and parameter domain. `org.openmatrix9.short_line.v1` records the intended Line identity. The reader accepts the marker only with value `1` and the exact degree, dimension, pole count, rationality and knot-count constraints; otherwise that object is not projected as editable geometry. The cold export comparison verifies the decoded Line coordinates and domain, and admits the native NURBS class only with the corresponding diagnostic. The diagnostic explicitly discloses the representation and warns that external edits can remove or invalidate metadata.

An open line that becomes too short after a root placement is also encoded this way; initially invalid polyline candidates fall back to polycurve construction. Real 3DM fixtures verify a non-unit line domain, a scaled root line, a polycurve with a tiny segment, and a Top11 Split of a tiny NURBS with two short-line cutters. The invalid-metadata fixture is refused for that object; when the marker is removed, the reader exposes the actual NURBS instead of inventing a Line. Preserve mode currently retains the marked object without exposing it for editing. Foreign applications may remove the marker, and actual Rhino or other independent-editor interoperability is not established. Short children that become invalid only after a parent polycurve placement, very large coordinates, arbitrary nested placements and retained-current edits of marked lines remain open; unsupported cases must continue to fail rather than silently change geometry.
