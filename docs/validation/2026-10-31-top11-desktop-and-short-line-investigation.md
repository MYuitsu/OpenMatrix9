# Top11 desktop observation and short-line 3DM investigation

On Windows x64, the standalone debug executable was built with `CARGO_TARGET_DIR=L:\om9-target` and `cargo build -j 2 -p om9-app --bin om9`. Its SHA-256 was `f71cfa806e2d8d1c280db77387fe7d1fbd383ddf60b27693eaa6c8384fb75623`. The checkout was dirty; HEAD was `89ef2676b597ebc5ab38fa5c6acf0ad47a2f261b` and does not alone identify the source used.

In a real Windows application session, a line was created via the command line, selected by mouse, and duplicated in place from the Top 11 toolbar. Control Points was toggled on and off. Move was then invoked from the toolbar with entered points `0,0,0` and `0,5,0`: a selected copy appeared shifted in the Top viewport while the original remained visible. The Undo toolbar button restored the overlapping appearance; Redo restored the shifted appearance. This is a visual observation of one example, not a measured model-coordinate or persistence assertion. No screenshot or document was saved. An attempted Save As was left open after the automation could not target the filename field even after reactivation and one retry. Human M03-UI acceptance and broader command/geometry coverage remain open.

The pinned openNURBS SDK's `ON_LineCurve::IsValid` treats endpoints as coincident using `ON_3dPoint::IsCoincident`, whose absolute and relative thresholds are defined by that SDK. Thus even mathematically distinct endpoints can fail the native geometry check. The existing test's `2e-10` mm cutter triggers this behavior. An exact degree-one native NURBS can represent the same endpoints, but changes the native object class; current import/export verification expects `ON_LineCurve` and cannot silently substitute a NURBS without changing interoperability semantics. A lossless, explicitly disclosed policy still needs design and roundtrip validation, including independent editors and nested polycurves. This source investigation is not an openNURBS measurement batch.
