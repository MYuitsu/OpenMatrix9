# Selected-object highlight latency — 2026-11-02

The user reported a long delay before the selected object's purple outline appeared. The fixture is the saved 21-cavity BRep dice (23,368 display vertices, 41,847 triangles), the default Windows debug build, and four visible viewports.

Before the change a direct controller probe measured about 115 ms per `retained_usage_with_held_usage` call for the current document with no Undo owner. The same fixture measured about 92–107 ms for one object pick, 119 ms for portable object info and 920–937 ms for the exact native measurement. Those are separate short debug measurements, not a sampled profile or a full click latency decomposition. The native measure reconstructed an independent shape and synchronously computed validity, bounds, area and volume for the label.

The coordinator now caches a validation proof for an unchanged immutable owner not covered by an Undo entry, using a weak identity reference and proof limits; changed owners or tighter limits are validated again. A short repeat of the direct selection probe measured 56 µs for the first call and 26–27 µs for three later calls; setup had already warmed the proof. It is not a full UI measurement. Normal object selection reuses the already sorted, revalidated ambiguity candidates rather than picking the same mesh twice.

The BRep Object Info overlay now requests the same exact existing measurement on one bounded background worker using an immutable document snapshot. It draws no measured label until that result arrives; stale document, session, geometry, placement, unit and limit keys cannot publish. The worker reconstructs its own native shape rather than sharing a mutable native handle. A focused test also ran independent native measurements concurrently; it is limited evidence and does not certify OCCT thread safety generally. Non-BRep information follows the existing synchronous path. Geometry, selection rules, Undo and exact measurement are unchanged.
