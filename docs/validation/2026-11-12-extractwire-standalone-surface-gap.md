# ExtractWireframe: standalone surface gap

A standalone planar NURBS surface was saved and reopened. Its current scene mesh contains segments along all four boundary sides and no interior display edges for this fixture. `ExtractWireframe` rejects the selected standalone surface; the document snapshot and a pre-existing Redo remain unchanged. The integration test `extract_wireframe_reopened_surface_display_boundaries_are_visible_but_refused_safely` establishes both facts for this fixture; it does not establish physical desktop rendering or coverage of other surfaces.

**Later implementation:** the user approved the scoped extension and the planar refusal above is historical. For a single visible and selectable standalone NURBS surface, the command now validates the source and placement, rejects periodic or certified closed axes and coincident boundary corners, and constructs four exact domain-boundary isocurves in Rust with the source placement. It reserves temporary/output memory and commits once. Mixed roots, interior isocurves, mesh wires and general seam handling remain outside this extension.

The reopened planar fixture checks the four distinct analytic boundaries, saves and reopens the output, and exercises Undo/Redo. A reopened half-cylinder fixture checks curve samples against analytic radius and height with translation, and Undo/Redo. A simulated memory-pressure failure and a closed-cylinder rejection preserve document and Redo; the former succeeds after pressure is released. The full wireframe suite passed 47 tests with four ignored, and the three focused surface tests passed. These are scoped fixtures, not certification of every surface, surface self-intersection, physical desktop interaction or native peak memory.

The half-cylinder test was subsequently strengthened and passed independently: it identifies all four expected corner pairs, rejects duplicate boundaries, and checks that sampled arc points lie on the intended half-cylinder and line points on the two end generators. This establishes the four distinct trimmed boundaries for that fixture, not for arbitrary surfaces.

The current standalone surface scene builder `surface_buffers` emits sampled boundary edges, not internal isocurves. The product's existing ExtractWireframe controller accepts B-reps and rejects standalone surfaces. The local command reference describes duplication of displayed surface/polysurface isoparametric curves and mesh edges, so B-rep edge extraction alone does not cover its stated scope. A possible first extension is exact surface-source boundary curves with placement and one transaction for verified open surfaces; it would not implement interior isocurves, meshes, all closed or periodic surfaces, or mixed roots. The user was asked whether to authorize that scoped extension; no implementation is claimed here.

## Implementation review before decision

For a single root, `extract_brep_edges` already captures the tracked document, checks the current scene epoch and source permissions, validates placement, and commits the completed curves through `commit_placed_geometries`. Its B-rep-only type check currently rejects `Geometry::Surface`. `DupBorder` already obtains exact NURBS boundary isocurves from the surface domain using Rust `surface_kernel::isocurve`, retains entity placement, and handles closed axes separately. This is a concrete reuse point for the proposed open-surface case; it is not evidence that ExtractWireframe may blindly delegate to DupBorder, because their command names, display semantics, selection scope and accounting differ. In particular, the existing multi-root path requires every root to be a B-rep, so the proposal leaves mixed roots unchanged. Any implementation must retain source and scene checks, use a single atomic commit, account for temporary/output allocations before publication, and refuse cases whose boundary cannot be established; it must not infer full displayed-isocurve support from four boundary curves. No behavior or source implementation changed in this review.


## Display-isocurve dependency audit (2026-11-13)

The current standalone NURBS surface buffer constructs surface triangles and only four boundary edge chains; it does not generate interior display isocurves. A source search for wire-density and isocurve-density identifiers found no active standalone model or scene setting: the native exchange reader exposes the 3DM wire_density attribute to retained exchange data, but this search did not find a path using it to build the live viewport. Therefore adding interior curves only to ExtractWireframe would not duplicate currently displayed curves in the tested standalone path. A usable extension needs a defined and persisted viewport density/parameter policy, a single policy shared with extraction, trim/periodic handling, and limits before selecting a default or modifying output. This is a source audit, not a claim that all 3DM metadata is discarded or that Matrix defaults have been established. No product behavior changed.


### openNURBS wire-density reference

The locally available openNURBS header opennurbs_3dm_attributes.h documents an object wire density of -1 for boundary wires, 0 for boundaries and knot wires, 1 for those plus a single interior wire when there are no interior knots, and N of at least 2 for those plus N-1 interior wires; its field default is 1. This is useful source-format evidence for preserving imported object intent, not proof that Matrix uses the same default, that all trim/periodic/face semantics are solved, or that OM9 currently imports this attribute into active scene state. The display and extraction paths still require an agreed shared implementation and bounded generation. No runtime change was made.
