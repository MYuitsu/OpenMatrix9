# Rhino 5 Undo: bounded local reference review

Scope: user-provided Rhino 5 managed and Ghidra reference files, inspected read-only for Undo architecture, not copied. Target context is `OM9-L3-01-02-007`. These are static observations from decompiler output, not a runtime benchmark, complete type recovery, disassembly verification or a license grant for recovered source.

- Managed `RhinoDoc.UndoRecordingEnabled` uses a native get/set bridge; a separate property reports active recording. Begin/End Undo use a serial number. Plugin callbacks have their own event lifetime.
- Native `CRhinoDoc::BeginUndoRecordEx` (Rhino.exe RVA 0x3f24e0) checks enabled/active state, creates and links a record, records a description and object serial context, and marks recording active. `EndUndoRecord` (RVA 0x3f2750) removes empty records, handles redo interaction and updates counters. Exact decompiler types and all error paths remain unverified.
- `FUN_1403f3260` walks an array of 24-byte entries in reverse and calls `FUN_1403f2a10`, which dispatches by entry type. Selected cases look up an object by runtime serial and call DeleteObjectHelper or UndeleteObject; another calls UndoModifyAttributes. This is evidence of operation/object-level records for these cases, not evidence that all geometry is stored as a small delta or shared.
- `CRhinoDoc::Undo` (RVA 0x3f3450) and `Redo` (RVA 0x3f37f0) guard against reentrant undo/redo, set up a record and call that dispatcher; the exact inversion/lifetime behavior of every action is not established.
- `UndoRecordCount` (RVA 0x3f3b60) and `UndoRecordMemorySize` (RVA 0x3f3bb0) use cached values and calculate from record data when the cache is empty; `EndUndoRecord` updates accounting, and `CullUndoRecords` accepts count and byte limits. These are accounting observations, not proof that every Rhino operation avoids other full scans or hashing.
- `ClearUndoRecords` also clears several tables and, when requested, purges deleted objects; this indicates retained deleted objects exist in relevant flows. It does not specify BRep geometry layout or prove when geometry is copied.

Comparison: OM9 stores before/after `Arc<Document>` references in `UndoEntry` and `validate_retained_owners` currently revisits distinct retained documents and validates their geometry. The separate 21-cavity debug run measured 1212.506 s with Undo and 120.182 s with Undo disabled; it does not isolate exactly which component caused the gap or measure Rhino. Proposed OM9 direction is Rust-owned per-change journal and/or trusted immutable validation and usage caching, following profiling and independent security/budget/Undo tests; no recovered native code was copied and no behavior change is authorized by this analysis alone.

Remaining: compare native disassembly to pseudocode for the selected record dispatcher, trace creation of Boolean object events and payload ownership, verify Rhino version/binary provenance and run controlled Rhino fixture if available. Do not infer delta compression, snapshot absence, hash policy, or speed parity.
