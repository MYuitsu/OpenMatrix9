# STL staging-file readback

The previous STL atomic writer validated the generated triangle stream, flushed and synchronized its temporary file, then renamed it to the destination without reading that file back. The application writer now computes SHA-256 while the buffered file writer writes, closes the flushed/synchronized stream, and independently reads the temporary file in bounded 16 KiB chunks. It checks the `84 + 50 * triangle_count` file length, encoded count, and digest of all bytes before taking the publication lock and atomically replacing the destination. Cancellation is checked before and during readback and again at the publication boundary. On failure, the temporary-file guard deletes the staging file and the existing destination remains unchanged.

The unit fixture writes a real binary STL, checks a matching file, then tests single-byte corruption, an incorrect triangle count, truncation and prior cancellation. It explicitly attempts publication of the corrupted stage over an existing destination and checks the old bytes remain. The existing streaming-cancellation, quantization-failure and successful replacement tests remain applicable. SHA-256 is computed under the buffer, so the encoder's individual float writes do not each require a hash update. Readback adds a complete file read and hashing; runtime/peak effects have not been measured on release or large production meshes.

On the default-feature E: debug build with `-j 2`, all 9 application worker/cancellation tests and all 42 STL integration tests passed after the final buffered implementation. The 11 exchange encoder tests also passed; no exchange encoder code was changed in this slice. No desktop session was operated.

The original readback check established consistency between the bytes handed to the file writer and the bytes read from the staged file, within the limits of the hash and filesystem, plus basic STL size/count consistency. The subsequent local triangle decoder is described below. Neither establishes manifoldness, self-intersection freedom, source-to-mesh deviation or globally bounded geometric error. Whole-mesh topology and accuracy oracles remain part of P3a. This is not evidence of UI worker integration, a process-memory ceiling, or desktop responsiveness.

## Encoded triangle decoding

The staged-file pass now independently decodes every 50-byte binary triangle record in fixed 16,000-byte blocks, checks that encoded coordinates and normals are finite, the triangle has nonzero area and the normal agrees with its winding. It still hashes all actual bytes and checks count and length before publication. It does not reconstruct indexed topology or compare triangles to canonical geometry. A new unit fixture changes a vertex to NaN, collapses two corners, or reverses the encoded normal, and recomputes the expected file hash each time; all three are refused, establishing that these checks are not merely hash comparison. A valid encoded triangle is accepted.

The application worker/cancellation unit suite passed 10 tests and the application STL integration suite passed 42 tests with the decoder on E: default features, `-j 2`. The checks have not been benchmarked in release on large files; 16,000 bytes is the fixed local block, not a bound on the rest of export memory. This does not change the independent encoded-topology, self-intersection or global-error limitations above.
