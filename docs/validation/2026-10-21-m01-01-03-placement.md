# Object placement write through SDK v1 — 2026-10-21

A plugin can now set an object's affine placement matrix through the document transaction.
The slice belongs to `OM9-L2-01-03` (`OM9-L3-01-03-002`, typed scene entity records).

## Changed

| Layer | Change |
|---|---|
| Public SDK | `Host::set_object_placement(id, [[f64;4];4])` and `ObjectSetPlacement`; capability entry. |
| Host | Validates the matrix with `Transform::validate` (finite, last row `[0,0,0,1]`, invertible linear part), requires the object to exist, and stages `Mutation::Placement` under the existing one-source-write rule. An object created in the same command is refused because its insert already carries the placement. |
| Example plugin | `PlacementDemo` moves an existing object by `(10, 20, 30)` mm. |
| Tests | Host test for a valid translation (commit + Undo restore), non-affine row, singular matrix, created-in-command refusal and the attribute conflict; native DLL test for the translation, Undo and Redo. |

## Semantics fixed by this slice

- The matrix is row-major, object-local to world, and must be a finite affine transform
  with an invertible linear part; otherwise it is a `placement` refusal.
- The write is one source write like attributes/rename/layer, so mixing two kinds on one
  object in a single command is a `conflict` refusal.
- The object must already exist; a command cannot retro-place an object it just created
  (the insert already carries the placement).
- Undo restores the previous matrix exactly; Redo re-applies it.

## Not proved here

- Nested object placement, instance/block transforms and gumball interaction remain at their
  owners.
- An object created in the same command cannot be placed afterwards; the plugin must set the
  matrix through its own construction data or in a following command.
- macOS host and plugin execution are unverified; interactive UI acceptance was not
  performed. No manual or M09 gate was promoted.
