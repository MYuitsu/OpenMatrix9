# Project state and save requests through SDK v1 — 2026-10-21

This is the first file-lifecycle slice: a plugin can read the host project's path and dirty
state and request one atomic save after its command commits. It does not open, create or
replace the active document, so the plan's "no document swap inside a command" condition
holds. The slice belongs to `OM9-L2-01-12` (`OM9-L3-01-12-005`).

## Changed

| Layer | Change |
|---|---|
| Public SDK | `ProjectInfo { path, dirty }`, `Host::project_state`, `Host::save_project`; two requests and capability entries. |
| Host | A `ProjectState { path, dirty }` snapshot is attached to the staged run by the app; `project_state` reports it and `save_project` refuses an untitled project before commit and otherwise stages `save = true`. `PluginRun` carries the flag. |
| App | `run_plugin` snapshots `file.path` and `is_dirty()` before the plugin runs; after a successful publish it calls the existing `begin_file_operation(FileKind::Save)` — the same atomic archive save path with fingerprint/receipt — and reports a save failure as a `Warn` event instead of turning a committed command into a failure. |
| Example plugin | `ProjectDemo` reads the state and, with `{"save":true}`, requests the save. |
| Tests | Host test for the untitled refusal, the attached snapshot and `PluginRun.save`; native DLL test that saves a real `.om9`, dirties it with `CreateProfile`, runs `ProjectDemo {"save":true}`, then reopens the file and compares the entity count. |

## Semantics fixed by this slice

- `project_state` is host file identity, not document state: `path` is the last opened/saved
  path (absent for untitled) and `dirty` compares the document to the last saved/opened
  fingerprint.
- `save_project` is staged, not executed inside the command: the transaction commits first,
  then the host saves through its atomic save path. An untitled project is refused before
  commit (`save`), so no command half-applies.
- A save failure after commit is a `Warn` event and the document stays dirty; the command is
  still reported as committed because its edits were published.
- A plugin cannot open, create or replace the active document; those stay interactive host
  operations, which is exactly the plan's required boundary.
- Reading project state and requesting a save stage no mutation on their own.

## Not proved here

- A plugin cannot open, create, replace or Save As a project; those remain interactive host
  operations. A plugin cannot choose a save destination.
- Recovery from a failed write (partial file, disk-full) is the file owner's existing
  behaviour and was not re-exercised through the plugin path here.
- macOS host and plugin execution are unverified; interactive UI acceptance was not
  performed. No manual or M09 gate was promoted.
