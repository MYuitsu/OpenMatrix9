# STL topology scratch lifetimes

STL topology analysis previously retained its face and edge maps, triangle union-find arrays and vertex fan map simultaneously. It now makes an edge/face pass, releases those maps and union-find arrays after counting their results, then builds and analyses vertex fans in a second pass. It retains the same input soup, checks allocation failures and cancellation, and does not alter tessellation, the exported triangles or tolerance. The additional pass can cost CPU; the allocator and concurrent memory use determine how much process peak is actually saved.

One isolated process per version ran the same `om9-app` release `stl_memory_probe` dense case on Windows, E: target, `-j 2`: radius 12 mm, requested 0.001 mm, angle 0.3 rad. Both reported 241,322 triangles. Before: 992.215 ms, peak process commit 215,203,840 bytes and peak working set 209,788,928 bytes. After: 971.007 ms, peak process commit 198,733,824 bytes and peak working set 193,908,736 bytes. The commit peak fell by 16,470,016 bytes (15.7 MiB, 7.7% of the baseline process peak). Each is a single run under uncontrolled system load; timing differences are not a reliable speedup claim. Peaks cover the entire process, not just the Rust maps or OCCT, and may depend on the allocator. The probe compared triangle counts and output size, not byte-for-byte STL equality.

All nine exchange STL policy tests passed, including cancellation at checks spanning the two passes, plus 13 writer/topology unit tests and all 47 app STL integration tests, including analytic sphere sampling, periodic NURBS, cavities, quantization and destination preservation. Public-source audit reported no errors; artifact pruning removed no runs. These regressions do not prove equality for every model or a global error bound.

The topology scratch sets and native tessellation are still not comprehensively measured or reserved against the shared RAM budget. This does not complete the background worker admission, 60% managed-memory gate, large-model benchmark, STL accuracy certification or desktop validation. The current release probe is a test executable, not a new user-facing OM9 build.
