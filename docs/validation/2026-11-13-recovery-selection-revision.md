# Recovery when selection changes and returns

The ExtractWireframe/DupBorder and ExtractIsocurve-start recovery targets previously compared the current set of selected objects but not the selection revision. In a simulated-pressure regression, changing the selection away and then back to the same object did not make the ExtractWireframe retry stale; it could proceed to Undo reclamation. The pre-fix run stopped at the ExtractWireframe case, so it did not independently establish the same outcome for ExtractIsocurve.

Both recovery targets now retain and compare the existing root-selection revision before retrying or pruning Undo. ExtractIsocurve's asynchronous face-verification recovery context also checks that revision. In a planar-surface fixture, changing the selection away and back causes both tested retry paths to stop before pruning; document, Undo and an existing Redo remain unchanged. The focused test passed for both cases. The 77-test recovery UI group passed before the final test-only explicit Redo assertion was added; the strengthened focused test then passed. The asynchronous worker was exercised separately below.

The no-default-feature cargo check and debug application build succeeded with existing warnings, using `L:/om9-target-surface` and `-j 2`. This is a simulated managed-memory/controller test, not a physical RAM exhaustion or desktop interaction test. The first-target application window was not replaced.

## Worker follow-up

The focused `isocurve_worker_recovery_cancels_if_root_selection_changes_and_returns` test subsequently started the actual face-verification worker for a sphere, changed the root selection away and back without changing the face-selection revision, and exercised the recovery UI frame. The recovery context became stale, the pending worker was canceled, no Isocurve session was published, and document, one Undo and one Redo remained unchanged. This test manually prepared the recovery offer and running state; it did not induce a real memory failure. It verifies removal of the pending job and the immediate state, not the exact time at which the canceled native worker releases its resources. One focused test passed; it was added after the 77-test group above. Physical desktop and OOM remain unverified.

The focused test was strengthened using a 30,016-triangle sphere: it observed the worker active before cancellation, waited until its active flag cleared and the managed kernel reservation returned to at most the pre-worker baseline, then rendered another UI frame and rechecked that no stale Isocurve session appeared and document/Undo/Redo stayed unchanged. One focused execution passed. The active flag and managed counter do not measure process working set, native allocations or the precise instant of release, and this remains a controlled test rather than physical OOM or desktop evidence.
