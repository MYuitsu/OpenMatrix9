# STL encoded vertex identity ambiguity

Binary STL stores triangle coordinates without vertex indices. The writer already retained an encoded-position map to reject different input positions collapsing through `f32` quantization. It now also reports when two distinct used soup indices have the same encoded position, including signed-zero normalization. This needs no additional per-vertex map. The atomic export receipt, human-readable message and MCP expose the ambiguity; existing writing entrypoints remain wrappers, and the result is returned only after staged-file verification and publication succeed. No vertices are merged, triangles changed or open exports refused by this diagnostic.

The exchange policy suite passed ten tests, including a cube whose repeated references reuse the same indices and two coincident separately indexed triangles. The app integration fixture confirms that two coincident selected open objects retain two source-scoped components while reporting the STL identity ambiguity. The MCP fixture checks the structured field. Twenty-two app STL session unit tests passed, including cancellation and destination preservation; public source audit reported no errors, and artifact pruning removed no runs. The final integration fixture passed again after the message was clarified. The full 47-test STL integration suite was not rerun for this change.

The flag indicates a potential ambiguity, not necessarily an error: distinct indices may be intended separate objects, shells, or an unwelded seam of the same source. It does not identify affected objects, count contacts, detect intersection between faces, reconstruct or validate encoded topology, or prove watertightness. A false flag also does not prove those properties. Distinct input coordinates that quantize to the same position remain a separate rejection. `watertight` retains its existing source-scoped indexed meaning for compatibility; the receipt message states that scope. Runtime memory and desktop behavior were not measured.

## Conditional encoded combinatorial result

The receipt now additionally provides `encoded_closed_by_topology_checks`: `true`, `false`, or unknown (`null` in MCP). When no distinct *used* indexed vertices share an encoded position, exact-coordinate indexing of the encoded vertices is injectively equivalent to the indexed soup. The writer already rejects new quantization collisions and verifies non-degenerate triangles and orientation, while the staged file is read back and matched to the encoded stream hash. Under those conditions the existing indexed edge, orientation, fan and duplicate results therefore apply to exact-coordinate indexing of the published bytes. When identity is ambiguous, this encoded result is unknown rather than copied from source topology. This is an inference from the checked mapping and readback, not an independent general topology reconstruction.

Two integration fixtures passed: an open authored triangle reports `false`; a closed tetrahedron reports `true`, while two coincident closed tetrahedra report unknown although both indexed sources are closed. An independent scan of the actual decoded STL confirms edge incidence two for one tetrahedron and four for the coincident pair. The existing coincident open-object case remains unknown. The MCP profile test verifies the boolean/null relationship and the existing field. The full 49-test integration suite was not run after this change. Public source audit reported no errors and artifact pruning removed no runs.

The result uses exact encoded coordinate equality, not a downstream reader's tolerance-based welding, object ownership or an independently certified solid. It does not check geometric self-intersection, shell containment, material orientation or global source deviation. A `true` result must not be interpreted as a printability or global manifold certificate. `watertight` remains the existing source-scoped field for compatibility.
