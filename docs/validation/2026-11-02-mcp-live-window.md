# MCP attached to the interactive OM9 window

2026-11-02, Windows x64. The existing `--mcp` server owns an independent, headless Controller. The new `--mcp-live` stdio proxy locates one interactive bridge and forwards requests to the owning UI thread; the GUI's Controller, document, selection and Undo/Redo remain authoritative. The GUI starts a loopback-only listener on an ephemeral port, publishes a random per-window bearer token and address under the current Windows user's LocalAppData, and removes the registration on normal close. Requests are bounded; a wrong token is rejected. This is a local-user integration, not an internet-facing service or isolation from other processes running as the same user.

The proxy starts even when no GUI exists. Tool calls fail clearly if no live bridge is reachable, and refuse to choose if more than one bridge is reachable. Windows from older builds without a bridge cannot be discovered. `om9_new`, `om9_open` and simulated `om9_ui` are not advertised and are rejected; opening and replacing documents remains in the GUI. `om9_save` uses the GUI Controller's file lifecycle, refuses a new destination that already exists, and leaves an existing GUI file operation untouched. A running GUI remains responsible for prompts, document state and repainting. Headless `--mcp` is retained unchanged.

Validation: `cargo check -j 2 -p om9-app --bin om9` passed; `cargo rustc -j 2 -p om9-app --lib --profile test -- -C debuginfo=0 -C link-arg=/DEBUG:NONE` built the test binary, and two `mcp::live::tests` passed: actual local authenticated transport to the Controller, wrong-token refusal, registry cleanup, UI-controller command/Undo/Redo, save/clean file state, and keeping an existing file operation. The final binary was linked with `cargo rustc -j 2 -p om9-app --bin om9 -- -C debuginfo=0`; the usual copy to `debug/om9.exe` was blocked by an already running window, so the freshly linked `debug/deps/om9.exe` was copied to `debug/om9-mcp.exe` (SHA-256 `da0cb40282ae7be36c8c8f295c383d41ad0ddd330616b0e131befa8e6c0eab94`). Earlier a GUI process of the same implementation before the file-operation guard was opened; direct stdio MCP initialize/tools/list/state returned its actual document, and a Box was created and undone in that window's Controller. Physical display/GPU presentation, a newly restarted Codex session, multiple concurrent GUI windows and the final build's actual GUI were not manually verified.

On this machine `codex mcp add om9-live -- L:\om9-target\debug\om9-mcp.exe --mcp-live` is configured globally, with tool timeout 600 seconds; `codex mcp get om9-live --json` confirmed it. The desktop shortcut `OpenMatrix9 MCP.lnk` points to that same debug binary. An already-running OM9 executable cannot be updated in place; the user must save work, close the old window and launch the shortcut to use the final guard. This is a local development binary outside the checkout, not an installer or release; rebuilding, pruning that target or moving it may require updating the shortcut and Codex config. Codex may need a new session or restart to discover a newly configured server. The live test's Box was undone, leaving a redo entry in the earlier empty test window.
