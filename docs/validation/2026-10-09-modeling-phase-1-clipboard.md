# Phase1 — native clipboard and bounded native workers

Implementation: Rhino5 native geometry clipboard in both directions through `Copy3dm`/`Paste3dm`, the File menu and Ctrl+C/V in the OM9 viewport/model tree. Text controls retain text shortcuts. Copy reads the current selected geometry; CAD stays CAD, native Mesh/Cloud serialize their actual data. Paste creates independent editable objects in one Undo transaction. It supports the already accepted Phase1 geometry scope, with normalized units and current placement; history/render are outside this working mode.

Run [the clipboard candidate](H:/FreeCAD-src/build/om9-clipboard-sdk/bin/FreeCAD.exe), activate OpenMatrix9, create/open a project, select geometry in Rhino5 and Ctrl+C, then Ctrl+V in the OM9 viewport. Draw/edit, select the desired current objects, Ctrl+C, then Ctrl+V in Rhino5. The clipboard is a raw V5 archive in `Rhino 5.0 3DM Clip global mem`; no user file dialog is required. Native Rhino command `CopyToClipboard` corresponds to Ctrl+C; `Copy` duplicates geometry interactively.

The native worker budget is `max(1, floor(0.60*N))` for available logical CPU threads, reduced by actual independent tasks and the RAM heuristic. On this24-thread machine the target is14, not a fixed4-thread ceiling. Workers use BelowNormal priority; small workloads remain serial. This bounds the worker count, without guaranteeing an exact CPU percentage for other applications. Native SDK parsing/writing and process-global diagnostics remain serialized. Independently owned OCCT assembly/healing/validation and staging use native threads; main-thread Qt/document mutation stays serialized. Background work releases the Python GIL and keeps a modal progress event loop alive; cancel waits for active native tasks and joins before cleaning staging.

The fix materializes prior MIME data, restores it on failure only while the clipboard sequence is still owned by this operation, and preserves a newer owner's data.
