# Undo shared B-rep source inventory

The full Undo memory inventory previously deduplicated document allocations and resource payloads but did not deduplicate the shared immutable B-rep source across document revisions. A synthetic B-rep with a 1 MiB source, moved three times, yielded 3,232,550 bytes of Undo memory even though the current document also owned that same source. This could trigger unnecessary oldest-Undo eviction under the configured soft budget.

The inventory now seeds source allocation identities from the live world and scope/savepoint worlds, then counts each history-only B-rep source once. A document's own storage already deduplicates aliases within that document, so repeated aliases in one document are skipped before cross-document subtraction. Separate allocations with identical source text remain separate. This changes the Undo accounting used for retention, not the canonical geometry, source identity, checkpoint or structural admission limits.

The red/green regression confirms three placement steps stay under a 1 MiB Undo policy while their shared source is live, then counts it once when only history owns it and checks Undo and Redo. A second test covers two equal but independent source allocations and a same-document alias, counting two allocations rather than one or three. The complete `om9-core` test command passed, with two existing ignored mesh benchmarks and one existing unused-mut warning; application regressions passed 11 gesture, seven Gumball and four Undo-settings tests. Public source audit reported no errors and artifact pruning removed no runs.

The fixture uses a valid portable B-rep snapshot with a synthetic 1 MiB source, not a kernel-parsed manufacturing model. The identity index adds allocation and the within-document alias scan is quadratic in B-rep count; full inventory cost and temporary-index admission are not benchmarked. Owners retained solely by external captures are not included in this Undo-specific exclusion. Other shared geometry owners, aggregate 256 MiB hard limit, full 60% managed accounting and desktop behavior remain open. The preceding isolated release bundle predates this fix.

An external-document registry entry is a weak reference to the document allocation, not a separate capture-lifetime token. If Undo itself continues to own the document, that weak reference remains upgradeable after an external capture is dropped. Therefore an upgrade alone cannot safely establish that an external capture still owns the data for Undo categorization. Exact attribution needs explicit capture lifetime tracking and a lock-order-safe interaction with publication and history trimming; treating every upgradeable entry as an external owner would risk undercounting Undo indefinitely. The current conservative exclusion was not widened on that basis.
