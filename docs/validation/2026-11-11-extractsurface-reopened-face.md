### UI-mediated reservation growth

The worker initially admits up to 16 MiB (or its calculated metadata floor). When Rust output or scratch needs more, it retains the existing reservation and sends a growth request to the UI. The controller samples current scene/auxiliary held usage and requests a separate Kernel allowance, first in a minimum 64 KiB quantum and, on budget refusal, retrying the exact additional amount. The worker merges only a wholly pending allowance from the same account and class; no existing owner is uncharged during handoff. It can cancel while waiting, including after a credit has been sent. Construction continues only after admission.

Controller fixtures use a deliberately small 4 KiB initial reservation: Extract Surface grows and commits, a competing reservation causes refusal with document/Redo preserved and permits retry, cancellation before and after sending credit releases the reservations, and a scene change produces a stale-result refusal. A Shell fixture also grows and checks volume and Undo. Core tests check the reservation merge and rejection of foreign, wrong-class and partly allocated guards. Ten external-reservation regressions, 12 large library tests, 70 Solid input tests, five large egui tests, the no-default check, public-source audit and debug build passed.

Earlier tests forced growth from 4 KiB. The later 22-source workload below demonstrates real output above 16 MiB; it does not bound OCCT native allocations or measure desktop responsiveness. Growth can be refused by current managed, physical or commit budgets. The worker waits for UI polling, which may be deferred during an active gesture; the UI does not join the worker. Small displays, scene preparation and commit remain synchronous.

On the independent 22-source workload in debug, one run measured transaction 9,480 ms, scene preparation 3,234 ms and longest poll 12,723 ms; the previous trial measured 10,403/6,787/17,200 ms respectively. Two subsequent release runs passed and measured transaction 495/480 ms, scene preparation 171/161 ms and longest poll 669/644 ms. The pre-change release baseline was 638/166/807 ms, respectively; previous baseline runs measured max poll 804/802 ms. These sequential measurements were not load-controlled; they do not establish worst-case latency, desktop responsiveness or native peak. Small batches and multi-document worlds retain the previous path, and the 20-insert threshold has not been tuned. Near-budget cases may incur a second validation if the tighter attempt fails.
