# Viewport camera and instance snapshot diagnostics

The existing geometry-upload counter measures retained vertex/index uploads and does not count per-pass camera or instance buffers. `SceneBatch` now reports the initialization byte lengths of its immutable camera and occurrence snapshots. Opt-in viewport diagnostics accumulate these separately for the Shaded main scene pass; they do not include ghost scene passes, line overlays, driver padding, retained geometry or work on the physical display. Counters are not GPU-residency or process-memory measurements.

On the default-feature E: build with `-j 2`, the four-object/four-viewport fixture ran four Perspective camera-only frames: main-pass snapshots initialized 320 camera bytes and 1,520 instance bytes in the moving viewport. The three unchanged viewports added zero snapshot bytes, and retained geometry-upload counts did not increase. The result demonstrates a remaining per-frame instance buffer creation/upload in this fixture; it does not show a general byte rate, CPU/GPU cost or desktop frame-rate effect. The GPU suite and the distinct-camera Gumball preview fixture ran on an adapter without skips. Persistent instance storage must preserve visibility/order, transforms, colours, in-flight lifetime and memory accounting before claiming the camera-only GPU goal.

## Immutable instance snapshot reuse

The initial implementation retained its latest serialized instance snapshot and an immutable GPU vertex buffer, comparing the full bytes on each pass. The follow-up below replaces this with a smaller identity-and-index key. A change in visible membership, draw order, transform or colour creates a new buffer instead of overwriting one already referenced by submitted commands. The current cached buffer is included in reported GPU buffer capacity. Clearing the batch releases its cache; wgpu commands may still hold retired buffers until work completes.

The camera-only single-object test failed before the change: instance initialization rose from 160 to 640 bytes over three frames. Afterward it remains unchanged while camera bytes increase. On the four-object/four-view fixture, four moving frames initialized 320 instance bytes after the change versus 1,520 in the earlier run; camera bytes remained 320 and the other three views added none. The changed-visible-set test confirms reinitialization when the object leaves and re-enters the frustum; the preview test confirms replacement on move and cancellation. Twenty GPU navigation/publication tests and ten GPU/egui Gumball tests passed serially without adapter skips.

These fixtures do not establish a desktop speedup or a global no-upload guarantee: different visible order/content, alternating views and ghost/overlay passes can still allocate and upload. The retained CPU cache is not yet admitted to the shared RAM budget; the GPU cache and buffers retained only by in-flight work are not yet governed by the 50% VRAM/OS budget. This partial optimization does not complete P0/P2 or prove pressure-safe retirement.

## Smaller cache key

The cache now holds a weak identity for the immutable occurrence array, the visible indices in draw order, and the exact static tint bits. All occurrence mutations go through `Arc::make_mut`, so a changed array has a different identity; membership/order and tint changes are compared separately. On a hit the renderer neither serializes instance bytes nor uploads the buffer. On a miss it serializes once and creates a fresh immutable GPU buffer. This key is conservative: a replaced but equivalent occurrence array causes a miss. For the single-visible-object fixture the reported retained payload changed from the previous 160-byte serialized copy to an 8-byte index allocation; this is not RSS and excludes allocator metadata and any weak-reference control block. The diagnostic field `shared_scene_instance_snapshot_cpu_bytes` now reports only visible-index allocation, not all CPU owner overhead.

The targeted size assertion failed at 160 bytes before the change and passed with 8 bytes afterward. Twenty GPU viewport tests and ten GPU/egui Gumball tests passed serially without adapter skips, including camera-only reuse, selection, preview/cancel, changed visibility and pixel checks. The index key is not yet charged against a global RAM reservation; GPU cache admission and in-flight retirement are also still open. CPU time, large models, real desktop responsiveness and physical presentation have not been measured.

## Scene replacement and in-flight snapshot lifetime

When the shared scene signature changes, the resource pool now asks each old scene's main and ghost batches to drop their optional instance snapshot before removing pool entries. Another viewport can still hold that old scene and its completed image; a GPU integration test confirms its logical index cache drops to zero without invalidating the image. `SceneBatch::evict_instance_snapshot` drops the cache owner only. Neither its diagnostic count decreasing nor this test proves that the driver has released GPU memory while commands are in flight.

An independent `om9-render` GPU test encodes two draws with different instance transforms into one submission, replaces the first snapshot, evicts the second snapshot and clears the batch before submission, then reads both images back. The first and second images retain their respective left/right positions. This proves the tested wgpu command lifetime and pixel result, not a general fence-based allocation ledger or GPU memory-budget enforcement. On the E: default-feature app build with `-j 2`, 21 GPU navigation/publication and 10 GPU/egui Gumball tests passed serially; the renderer lifetime test passed with `om9-kernel/3dm-brep` enabled. No adapter skip was reported.

## Encoded and in-flight instance tracking

The shared window resource pool now retains the unique main-scene and preview-ghost instance buffers used by encoded work, transfers them into a submission ledger when the window encoder is submitted, and removes each submission's reference only in the GPU queue completion callback. A buffer shared by views or overlapping submissions is counted once, with a reference count preventing early removal. This tracking persists when a scene cache owner is evicted. Opt-in diagnostics report encoded bytes, submitted bytes/count and their deduplicated union. These numbers can overlap the separately reported live scene cache and must not be summed with it.

GPU tests confirmed a 160-byte shared instance buffer is counted once across two viewport passes before and after submission, then disappears from the in-flight ledger after queue completion while its scene cache remains. A separate reference-count test verifies two overlapping submission owners remain counted after the first completes and disappear after the second. All 23 GPU viewport tests and ten GPU/egui Gumball tests passed serially without an adapter skip.

At that stage the partial logical ledger did not include live cache in its deduplicated union; see the follow-up below. It is not GPU budget enforcement or proof of immediate driver deallocation. It excludes retained scene geometry, camera and overlay snapshots, staging, targets, driver overhead and any work outside this window pool. CPU ledger storage, device-loss recovery and sustained-pressure behavior remain unverified. Queue completion is not physical presentation.

## Unique instance cache and in-flight diagnostic

The window resource pool now keeps weak references to scene slots so diagnostics can enumerate still-live main/ghost instance caches, including a previous scene still held by another viewport. The `unique_instance_bytes` diagnostic deduplicates those cached buffers by GPU handle against encoded and submitted instance buffers. It returns unavailable if a necessary lock cannot be acquired rather than returning a partial count. It is calculated only when diagnostics are requested; it is not yet an admission controller.

Tests verify that one 160-byte buffer shared by two viewport passes remains one 160-byte allocation while cached, encoded, submitted and after completion. Another test verifies that two independent main/ghost buffers total 320 bytes. A third evicts the old scene's cache while its buffer is already encoded and confirms the 160-byte allocation remains in the union through queue completion. All 25 GPU viewport and ten GPU/egui Gumball tests passed serially on the available adapter.

The figure is the logical wgpu buffer size for instance buffers in this window pool, not measured physical VRAM or a complete scene total. Camera buffers, geometry, staging, targets, driver overhead, CPU allocations, stress renderers and other pools remain outside it. The implementation does not yet enforce a RAM/VRAM cap or make a guarantee under device loss or memory pressure.

## Viewport render targets in flight

The shared window pool also tracks the colour, MSAA colour and depth textures referenced by its encoded viewport render commands. Unique target handles move from the encoded list to a reference-counted submission list and leave that list after the relevant queue completion callback. The diagnostic reports logical texture sizes assuming the RGBA8 and Depth32Float targets used by this path; it does not report driver padding or physical VRAM. The encoded/submitted union can overlap each viewport's live-target count and must not be added to it.

A 320×240 4× MSAA fixture accounts for three targets totaling 2,764,800 logical bytes. It resizes the viewport before submitting the old command and verifies those old targets stay counted through submission and disappear from the submission ledger after queue completion. A two-viewport test verifies six independent targets are accounted, while the shared instance buffer is counted once. All 26 GPU viewport tests and ten GPU/egui Gumball tests passed serially without adapter skips.

This ledger follows the window pool's viewport render submission only. It does not cover later eframe compositing/presentation use, targets allocated but not encoded, all live viewport targets as one deduplicated total, camera/overlay/geometry buffers, staging, driver overhead or other render paths. Queue completion does not prove physical VRAM was freed or the image was displayed. GPU budget admission, pressure handling and desktop performance remain open.

## Scene geometry buffers in flight

When viewport diagnostics are enabled before encoding, the window pool now records the actual wgpu vertex/index arena handles referenced by shaded document-scene and drag-ghost passes. It deduplicates shared handles across main/ghost scenes, MSAA scene variants and viewport submissions, retains encoded and submitted handles until the queue completion callback, and reports their logical buffer sizes as `unique_geometry_bytes` and `inflight_geometry_bytes`. Live scene enumeration uses nonblocking locks and reports unavailable rather than a partial union. This tracker is enabled only for the requested diagnostics; it is not GPU budget admission.

In the real egui/wgpu offscreen harness, a one-mesh scene allocates two arenas of at least 4 MiB total. Tests verify two viewports share and count those arenas once, submission overlaps the live cache without double counting, and live geometry remains after completion. A separate test replaces the document scene, drops the old view owners, and checks the old buffers remain in the submitted union until queue completion and then leave it. All 27 GPU publication tests and 20 Gumball GPU/egui tests passed serially on an available adapter; the user's own desktop Gumball acceptance remains separate.

These are wgpu buffer sizes, not measured physical VRAM or guaranteed driver deallocation. The count excludes upload staging, camera and overlay buffers, stress/cluster renderers, non-window queues and other owners; enabling diagnostics after a submission cannot retroactively record it. It does not sum the per-viewport target counts or enforce the requested GPU budget, implement batching, measure presented frames, or prove desktop smoothness. Diagnostic handle-list allocation and device-loss behavior also remain unmeasured.

## Window-wide target union

The opt-in interaction log's `viewport_counters` event now includes `window_targets`: logical bytes and counts for the unique live textures referenced by every viewport in the window, the additional encoded/submitted textures no longer referenced by those views, and their deduplicated union. Current 2D RGBA8 and Depth32Float single-mip targets are counted by dimensions, sample count and format; unknown target shapes, a mixed pool, busy locks or arithmetic overflow return unavailable instead of a partial total. Collection happens only for the explicitly requested interaction log and uses nonblocking pool locks. It accepts the actual window's entire viewport collection; a caller omitting views would produce an incomplete snapshot.

An offscreen four-viewport test checks the window live total against the four independently owned target totals. A resize test verifies old command targets remain in the union until queue completion, then leave the retired-command portion; it also checks a mixed pool and a held lock return unavailable without blocking. All 27 GPU publication tests passed serially after the initial addition; after the final checked-arithmetic change the two affected four-view and resize tests passed again. No adapter skip was reported. This remains a logical window-render snapshot, not physical VRAM: driver padding, eframe's later compositing and present ownership, staging, buffers and other GPU queues remain outside it. It does not enforce the GPU budget or establish desktop performance.

## Selected-adapter budget preview

An internal, safe-Rust preview computes separate values for half of reported dedicated capacity, 90% of the OS-assigned budget and the observed remaining OS headroom after current usage. The proposed configured ceiling is the minimum of the capacity/fallback, OS ceiling when known, and an optional lower caller limit. A zero caller limit is rejected and arithmetic is overflow-safe. Current OS headroom is a point-in-time sample, not guaranteed availability, and is not added to or substituted for a complete inventory of OM9 allocations. `enforced` is always false in this preview.

When an interaction log is explicitly enabled, the startup DXGI sample from the exact wgpu-selected DX12 adapter includes this preview. A GPU reported as integrated is flagged as requiring shared-RAM accounting and uses the unverified 256 MiB fallback; unknown/unsupported or Vulkan heap mapping also uses the unverified fallback. Reported adapter type is not an independent UMA proof. Vulkan raw heap samples remain visible, but the preview does not guess which heap is dedicated. The optional lower value exists only in the internal calculation: no setting, persistence, refresh on budget changes, RAM charge for UMA, resource eviction, allocation rejection or batched rendering has been implemented by this change.

Four unit tests passed for dedicated capacity, OS headroom/pressure, lower limit, integrated/unknown fallback, zero and maximum values, classification and serialized `enforced: false`. Three native GPU-query tests passed on available adapters; one discrete DX12 test adapter reported 12,701,401,088 dedicated bytes and an 11,896,094,720-byte local OS budget (a 6,350,700,544-byte 50% capacity preview), while another reported zero dedicated bytes. These are offscreen test adapter samples and do not prove which adapter the running desktop session uses. One interaction-log regression passed; the actual startup event has not been verified in a desktop run. No complete GPU accounting or actual 50% enforcement is claimed.
## Overlay buffers in encoded and submitted work

With interaction diagnostics enabled before submission, the viewport now tracks the actual wgpu overlay vertex buffers and per-pass camera/model uniform buffers in encoded commands and submitted work. Buffer handles are deduplicated, remain counted until the queue-completion callback, and are then released from the in-flight inventory. A window-wide diagnostic unions the live buffers from all supplied viewports with encoded and submitted buffers; the log emits `window_overlays`. It returns unavailable if a viewport belongs to another pool, diagnostics are disabled for a supplied viewport, or a relevant lock is busy. This diagnostic must be given every viewport and enabled before the tracked work; it cannot reconstruct earlier submissions.

The 27 serial offscreen `gpu_navigation_publication` tests passed without an adapter skip. The existing two-viewport fixture was extended to verify nonzero overlay buffers before submission, the same tracked amount while in flight, live-versus-command-only window totals, zero command-only bytes after GPU completion, and mixed-pool/busy-lock refusal. The 20 serial GPU/egui Gumball tests passed after the overlay tracking change and before the later log-only window aggregation change. Tests used the default-feature debug target on E: with `-j 2` and OCCT runtime paths. Public-source audit passed and artifact pruning removed zero runs.

These are logical `wgpu::Buffer::size()` values, not measured physical VRAM. Queue upload staging, pipeline/bind-group and driver overhead, eframe/other queues, stress renderers and diagnostics enabled after submission remain outside the inventory. GPU completion is not desktop presentation. This does not enforce the GPU budget, establish VRAM release, perform complete batching, or prove desktop smoothness; no release/desktop or matched performance measurement was collected.

## Scene camera buffers in flight

When viewport diagnostics are enabled before encoding, scene and drag-ghost camera uniform handles are now retained in the window's encoded/submitted inventory until queue completion. The per-viewport diagnostic reports the window-wide encoded, in-flight and deduplicated union byte counts; these are separate from the existing cumulative camera-upload statistic and overlay uniforms. Disabled diagnostics do not retain these handles for this inventory. The scene renderer returns the actual camera buffer used in its encoded pass so the diagnostic tracks ownership rather than extrapolating from frame count.

Twenty-seven serial offscreen GPU publication tests passed without an adapter skip. The two-view fixture verifies two distinct 80-byte camera buffers before and after submission and zero after completion; the Gumball ghost fixture verifies separate scene and ghost camera buffers. Four renderer tests passed, including comparison of four cameras encoded together with independent full-quality reference images, and 20 GPU/egui Gumball tests passed. The default-feature debug target was outside the checkout on E:, with `-j 2` and OCCT runtime paths where needed. Public-source audit passed and artifact pruning removed zero runs.

This is a logical wgpu-buffer inventory, not physical VRAM. Upload staging, pipeline/bind-group storage, driver padding, eframe presentation, stress/cluster renderers and other queues remain outside it. Enabling diagnostics after submission cannot reconstruct older work, and GPU completion does not prove presentation or deallocation. No GPU budget enforcement, complete batching, release/desktop acceptance or matched performance result is implied.

## Independent vertex and index arena capacities

New scene chunks now select vertex and index buffer size classes independently rather than making both buffers as large as the larger mesh stream. The initial chunk pair and existing size classes are unchanged. A resident scene fork for another MSAA pipeline now starts without allocating an initial pair that it would immediately discard; it still shares the original GPU arena handles and does not re-upload geometry.

For a synthetic 200,000-vertex mesh with six indices, the retained logical arena capacity was 14 MiB: the existing 4 MiB initial pair plus an 8 MiB vertex buffer and 2 MiB index buffer. The previous equal-size rule would allocate 20 MiB for that same sequence. The inverse fixture with three vertices and 550,002 indices also used 14 MiB. Tests check the actual wgpu buffer sizes, queued byte count, shared fork handles and zero pending fork uploads; the vertex-heavy case also verifies before/after pixel positions across queued scene draws. These fixtures include many duplicate vertices or triangles and do not predict savings on real scenes. Independent size classes may change how later meshes fit into chunks, so total allocation can differ in either direction on other sequences.

Seven serial renderer GPU tests passed without adapter skips, including four-camera image comparisons and MSAA. Twenty-seven serial offscreen viewport-publication tests and 20 GPU/egui Gumball tests passed. Builds used the default-feature debug target on E: with `-j 2` and OCCT runtime paths for the app. Public-source audit passed; artifact pruning removed zero runs.

These logical buffer capacities are not physical VRAM or a measured process peak. The change does not enforce the 50% GPU budget, implement over-budget complete batching, prove identical images for all meshes, or establish release/desktop responsiveness. The avoidance of the fork's throwaway initial pair follows from the construction path; no transient driver allocation measurement was collected.

## Allocate geometry arenas only for nonempty scenes

Scene construction no longer allocates the initial 2 MiB vertex and 2 MiB index buffers before any mesh is added. An empty scene and its MSAA fork therefore expose zero logical geometry-buffer bytes; the first mesh creates an appropriately sized pair. For the two asymmetric fixtures above, removing the unused initial pair reduces the measured logical capacity from 14 MiB to 10 MiB; the earlier 20 MiB comparison describes the original equal-sized rule for the same fixture sequence. This does not imply the same reduction for all geometry or that all viewport GPU resources are absent in an empty scene: render targets, overlays, pipelines and camera/instance buffers remain.

Seven renderer GPU tests passed, including an empty-scene encoded pass and four-camera image comparison. Twenty-eight offscreen viewport publication tests passed, including a new empty-to-filled scene transition and its geometry-buffer inventory; all 20 GPU/egui Gumball tests passed. No GPU adapter skip was reported. Runs used the default-feature debug target outside the checkout on E:, `-j 2`, and OCCT runtime paths for the application. Public-source audit passed and artifact pruning removed zero runs.

These are logical buffer capacities rather than measured physical VRAM. There is no release/desktop measurement, no general performance or real-model memory claim, and no 50% GPU budget enforcement or complete over-budget batching. Other resource owners and native/driver overhead remain outside this evidence.

## Minimum viewport target budget guard

Before creating or resizing normal document-viewport targets, OM9 now checks the logical minimum for two full-resolution colour images and the applicable depth/MSAA attachments against the selected-adapter budget preview. On Windows DX12 the preview uses the exact wgpu adapter's DXGI sample, the agreed 50%-of-dedicated capacity and OS budget after 10% headroom. Unknown or unsupported adapters, including the current Vulkan fallback, use 256 MiB and label the hardware ceiling unverified. If the minimum alone exceeds that ceiling or arithmetic overflows, OM9 refuses target creation, leaves the last completed image of the same document visible, and shows a viewport error. It does not intentionally reduce resolution, samples or object count. A viewport from a different document is not used as the placeholder.

An offscreen egui/GPU test injected a one-byte ceiling during resize and checked the old published texture, one pixel, and frame ID remained unchanged, then removed the limit and verified recovery. One arithmetic test covers one/four samples, invalid zero dimensions and overflow. Twenty-eight serial offscreen viewport tests and 21 GPU/egui Gumball tests passed with no adapter skip. The default-feature debug target was outside the checkout on E:, with `-j 2` and OCCT runtime paths. Public-source audit passed and artifact pruning removed zero runs.

This is only a necessary lower-bound check for a single viewport's targets. It does **not** reserve resources or enforce a window-wide/50% VRAM cap: current OS usage, geometry buffers, other viewports, retained or in-flight targets, upload staging, driver overhead, UMA RAM accounting, Vulkan heap mapping and dynamic pressure after target creation remain outside this guard. It does not implement the required complete over-budget scene batching or establish that target-plus-one-batch fits. A successfully admitted target can still fail under memory pressure. The simulated guard does not prove physical OOM handling, release performance or desktop presentation.

## Vulkan local-heap budget in minimum target guard

When the exact wgpu Vulkan adapter/device exposes `VK_EXT_memory_budget` and has exactly one device-local heap, the minimum viewport-target guard and diagnostic preview now include 90% of that heap's reported OS budget. Vulkan device-local or host-visible flags alone do not prove dedicated VRAM; the 256 MiB unverified hardware fallback remains the other ceiling. Multiple local heaps, unavailable extensions and non-Windows builds retain the prior unverified fallback. This is a per-target minimum check, not a reservation, a 50% VRAM guarantee, current OS headroom enforcement or complete batching.

Five budget calculation tests cover low OS budget, host-visible and multiple-heap ambiguity, discrete and integrated device types. Twenty-eight serial offscreen GPU viewport tests passed with an available adapter. A separate actual Vulkan query against the matching selected device passed: one local host-visible heap reported 12,701,401,088 bytes capacity and 11,896,094,720 bytes OS budget, with a second nonlocal heap; the extension was enabled. This is one momentary hardware sample, not a desktop rendering or pressure test. Tests used the E: debug target, `-j 2`; no matched release benchmark or full window-wide budget enforcement was established.

## Sampled OS headroom in minimum target guard

When the selected adapter provides both an OS budget and current usage, the viewport target minimum is now compared with the lower of the configured ceiling and `max(0, 90% of OS budget - OS usage)`. With no usage sample, the earlier configured ceiling remains in force. The guard uses a fresh sample only when creating or resizing targets; it can conservatively refuse when the full minimum includes resources that could otherwise be reused or retired. Refusal retains the last complete same-document image. The sample and comparison do not reserve memory: concurrent GPU work, staging, driver allocation and changes after sampling can still exhaust it. Full window inventory, UMA RAM integration and over-budget batching remain open.

Five budget tests cover a 4 GiB configured ceiling with only 512 MiB sampled headroom, no remaining headroom, and unavailable OS data. Twenty-eight serial offscreen viewport tests passed; 21 serial GPU/egui Gumball tests also passed, including the existing injected minimum-target refusal and recovery. Those tests do not inject the OS sample into the actual guard or create physical GPU pressure. Debug build on E: with `-j 2`; no release or desktop measurement.

## Window target inventory during allocation

Before a normal UI viewport creates or resizes its targets, the window now inventories the deduplicated known live targets and encoded/in-flight targets across its viewports. Their logical bytes are subtracted from the configured ceiling before comparing the new full-resolution target minimum. OS sampled headroom is a separate limit, avoiding subtraction of known targets twice from that sample. The inventory runs only when targets need creation or replacement, not on unchanged-target navigation frames. It uses nonblocking locks; if unavailable, the viewport retains its last same-document complete image and retries rather than allocating against an unknown inventory. Direct standalone viewport callers that do not supply a window inventory retain the individual-target guard.

A four-viewport offscreen UI test sets a ceiling larger than an individual viewport's needs but no larger than currently inventoried window targets, verifies a resize is refused with its prior texture intact, then removes the test ceiling and verifies recovery. Twenty-two serial GPU/egui Gumball tests and 28 serial GPU viewport tests passed without an adapter skip on the E: debug target with `-j 2`. The existing in-flight target tests verify target deduplication and retirement independently. The new inventory is point-in-time and conservatively includes old and replacement targets; it does not reserve GPU memory, cover geometry, overlays, staging, eframe, driver or other windows, establish UMA RAM accounting, or implement complete over-budget batching. No real GPU memory pressure, matched release performance or desktop presentation measurement was performed.

## Known scene buffers in viewport target admission

The normal UI's target-allocation inventory now adds unique known live, encoded and in-flight scene geometry and instance buffer capacities to the known window-target total, deduplicating shared buffer handles. Geometry buffers used by encoded shaded passes are tracked until queue completion even with diagnostics disabled; visiting arena handles on each encoded pass avoids allocating a temporary handle vector. Only target allocation or resize runs the full inventory, and lock contention defers allocation rather than assuming zero.

An offscreen scene-replacement test now submits the old geometry with diagnostics disabled and confirms it remains in the account until GPU completion; 28 serial GPU viewport and 22 serial GPU/egui Gumball tests passed on the E: debug target with `-j 2`. The tests cover resource tracking and existing window-target refusal separately; they do not isolate geometry as the sole cause of target refusal. Pending background scene-preparation outputs, overlays, camera buffers, staging, eframe, driver and other windows remain unaccounted; the result is a known lower bound, not a reservation or complete 50% GPU cap. There is no actual GPU pressure, matched performance benchmark, release or desktop evidence. Always tracking encoded scene handles may have a CPU cost that has not been measured.

## Overlay and camera buffers in viewport target admission

Target admission now adds known live overlay vertex buffers and encoded/in-flight overlay and camera uniforms to the same deduplicated scene-buffer inventory. Tracking those submitted buffers no longer depends on enabling interaction diagnostics. The inventory runs only when a viewport needs new targets; buffers in pending background worker results, uploads and staging, eframe, driver and other windows remain outside it. It is a point-in-time lower bound, not a GPU reservation or complete budget enforcement.

The diagnostics-disabled scene replacement fixture now confirms the old submitted camera and overlay buffers remain tracked through GPU completion. Twenty-eight serial offscreen GPU viewport and 22 serial GPU/egui Gumball tests passed on the E: debug target with `-j 2`; the combined-total assertion also passed separately after it was added. ## Viewport worker preparation inventory

GPU scene and overlay preparation jobs now register with their window pool from enqueue until execution exits. Target allocation is deferred while any such job is queued or running, including a canceled job that has not actually exited, because its partial allocations cannot yet be inventoried. When a job completes, its known geometry, instance and overlay buffer handles are registered until its result is received or discarded; the window inventory deduplicates those handles with live and in-flight resources. Superseded results are dropped. This does not reserve memory for the worker itself, limit concurrent work elsewhere, count pipelines, staging, driver or eframe allocations, or implement batching. Deferred allocations can delay viewport startup or resize; the impact has not been measured on desktop.

A controlled worker test with an actual 4096-byte GPU buffer verifies active preparation makes the inventory unavailable, a completed but unreceived result is charged, ownership remains charged through receive, and a canceled worker remains active until it exits. Twenty-two serial GPU/egui Gumball tests and 28 serial viewport publication tests passed on the E: debug target with `-j 2`. An initial full viewport run had 27 passes and one failure because an older test unwrapped the deliberately unavailable inventory while a canceled job was still running. The test now waits for actual worker completion and all 28 passed on rerun. No real GPU pressure, matched release latency, desktop or full-budget guarantee was established.
