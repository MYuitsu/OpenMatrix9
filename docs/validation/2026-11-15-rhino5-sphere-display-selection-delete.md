# Sphere display, selection and deletion: Rhino 5/Matrix9 versus OM9

Static, bounded reference review, 2026-11-15. No recovered source was copied and no product behavior was changed for this review. The user reports smooth interaction with 768 spheres. The screenshot says 768 surfaces were selected and shows apparently smooth shading; it does not measure triangle count, FPS, delete duration, sharing/instancing or the exact display settings.

## Main findings

1. **OM9 currently shades triangles flat.** The live SceneBatch shader computes a normal from screen derivatives of world position (`crates/om9-render/src/scene.rs:190`); its vertex output carries position and tint, without vertex normals. Cluster drawing uses the same approach (`cluster.rs:612`). The active viewport constructs SceneBatch in `gpu_viewport.rs:3484` and also uses it for moving/selected batches at line 1783. This makes lighting discontinuities between coarse triangles visible. MSAA addresses edge sampling, not this missing smooth-normal field. This is a concrete OM9 code finding, not an inference from the screenshot.
2. **The multi-object selection frame can be expensive even with a cached mesh.** `ui.rs:6328` includes the camera in its cache key. On a miss, lines 6354–6382 walk every selected object's display vertices, transform and project every point. Preparing one projector per pane reduced repeated matrix setup, but retained the per-vertex loop. Camera motion therefore invalidates this cache. This is an observable candidate for CPU cost, not a new isolated timing attribution.
3. **Rhino separates authoritative BRep geometry from derived mesh/display representations and retains caches.** Native `MeshCount` checks existing face meshes/parameters; `GetMeshes` collects existing face mesh pointers; `CreateMeshes` explicitly creates and installs a requested representation. `BrepDisplay` lazily allocates an object display structure and reuses it on subsequent calls. `Draw` reuses/delegates through that display structure. This does not mean geometry is approximate until export, nor prove a separate file, background execution, zero remeshing, or instancing across all 768 spheres.
4. **Native Rhino has normal-array rendering paths.** `FUN_1401b24f0` conditionally enables the normal array and supplies the corresponding stream to OpenGL. `FUN_1401a9d20` contains a smooth-shade path using a mesh vertex-normal array. These are evidence of available native rendering mechanisms. Unresolved virtual/display-engine calls prevent claiming that this exact branch rendered the user's screenshot. Smooth shading can hide lighting facets without a corresponding increase in triangle count; it does not repair a polygonal silhouette or alter exact CAD geometry.
5. **Object selection/deletion is distinct from tessellation or Boolean.** The inspected native Select path updates selection/highlight state and notifications. DeleteObjectHelper records an object-level Undo event in the inspected branch, unlinks/relinks object-list nodes and performs notifications. The BRep deletion notification frees its cached display structure. Relevant Undo paths retain deleted objects for restoration. These observations do not establish constant-time deletion or that every Rhino operation uses only tiny deltas. OM9 already batches multi-delete in one transaction (`session/subobjects.rs:294`); its remaining scene/admission/retained-owner work must be profiled rather than assuming it deletes one transaction per object or copies all geometry.

## OM9 engineering direction, not implementation approval

- Preserve the exact BRep. Add display normals derived from the corresponding source face where practical, or carefully smoothed within face/crease boundaries. Avoid smoothing across intended hard edges. Check sphere silhouettes separately from shading.
- Measure the selected-frame per-vertex projection independently. A cached object/selection bound or hierarchy is a candidate; conservative clipping and the approved selection-frame behavior require explicit design/validation. Do not weaken precise picking or source snap to optimize a decorative frame.
- Preserve mesh/display caches through camera and highlight-only changes. Profile delete preparation, scene publication and retained-owner/Undo accounting separately. OM9 already has shared buffers, cached camera projection and a single multi-delete transaction; reuse them.
- A useful next comparison is the same 768-sphere scene: idle/orbit with no selection, with all selected, delete, then Undo; record tessellation counts, visible pixels, frame gaps, operation time, RAM and retained history. No such matched Rhino/OM9 runtime comparison was performed in this review.
