# STL triangle finalization without a duplicate buffer

STL finalization formerly allocated another triangle vector sized to the complete input, then copied non-degenerate triangles into it. The input vector is private to the in-progress export, so finalization now compacts it in place, preserves order, periodically checks cancellation, rejects invalid indices and authored degenerates, and omits only already-permitted exactly collapsed generated triangles. On error the private work is discarded before destination publication; no document state is modified. The output keeps the original vector capacity, which can exceed its final length.

A red/green fixture verifies the retained sequence, omission count and reuse of the exact original vector allocation. Existing tests verify invalid authored triangles and indices and pre-cancellation; the whole group of 18 STL unit tests and 46 application STL integration tests passed in the default-feature debug build with `-j 2`. This removes a separate requested allocation of `12 * input_triangle_count` bytes for the second vector on this platform, but does not by itself prove the reduction in whole-process peak: allocator capacity, OCCT/native work, output soup and topology maps also affect the high-water mark. The existing 60% aggregate policy is not yet fully enforced.

## Release process comparison

The same eight-shared-sphere fixture used in [the earlier baseline](2026-11-03-stl-repeated-instances-release.md) was rerun after the change in a fresh release process, OCCT 8.0.1, `-j 2`, radius 5 mm, linear tolerance 0.005 mm and angle 0.3 rad. Both produced 159,600 triangles. Before: 498.717 ms and 99,811,328 bytes peak commit; after: 504.576 ms and 99,745,792 bytes peak commit. The difference, 65,536 bytes, is too small relative to process variability to attribute to this change. The eliminated second-vector request was 1,915,200 bytes for this fixture, but the process high-water mark may occur at a different stage. Each version was run once on an uncontrolled system, and executable/source versions differ; this does not establish a speed or process-peak improvement. Peak commit includes the process lifetime and is not OCCT-only memory.

The post-change executable SHA-256 was `802d854f20d8f76ce2139de7782ebc71cd9f571bd36d854348750a6916eeb2c5`, and probe source SHA-256 `0dd8849e3b2f61acfc4406128d4375b3f502a73c99a42ca376a75a58b378a125`. The probe source also gained separate snapshot-inventory reporting for another case between builds; that path was not used by this fixture. No desktop OM9 process was modified.
