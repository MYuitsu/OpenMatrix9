# Viewport scene/worker shared-buffer lease — 2026-11-05

The previous viewport preparation reservation charged a whole worker scene on top of the whole live scene, although the render-buffer `Arc`s were shared. It could reject a valid preparation when enough RAM existed for the live buffers and new snapshot metadata, but not another full copy of those buffers.

On first viewport snapshot for the current scene, the Controller now admits a shared CPU-cache lease for that scene's distinct render buffers. The Controller and all presentation snapshots for that scene hold the same `Arc` lease. Controller-held usage excludes those bytes while the account lease includes them; snapshot metadata is reserved separately. Preview changes and same-key workers reuse the same snapshot as before. Scene replacement drops the old scene before releasing the Controller's lease; any old worker snapshot retains the lease until its own scene is dropped. Controller field order also drops the scene before its lease. New/Open transfers the old shared account using the existing replacement machinery. The STL capture's auxiliary calculation accounts for the separately registered buffer lease, avoiding a false accounting error; detached export may still conservatively double-charge scene bytes.

- Five presentation owner tests pass. Another checks that Controller held usage drops by exactly the shared buffer bytes, the shared reservation contains the buffer plus snapshot metadata exactly once, STL capture still accepts the source, and the old snapshot remains charged after an edit until dropped. A separate New-document case holds an old snapshot across replacement and verifies the lease is released only after the worker owner drops. These tests use controlled managed budgets, not OS exhaustion.
- Forty-four STL cancellation/admission tests pass. Twenty file lifecycle, 18 clipboard (three native cases ignored), 11 gesture and nine interactive RAM tests pass; six large RAM fixtures were ignored in this run. Twenty-seven offscreen GPU/egui viewport/Gumball tests pass without adapter skips (53.24 s). The final added test changed test code only after that GPU binary was built.
- The focused Top11 empty Duplicate/Trim completion test also passed after the scene-clear change (23.09 s build, 0.01 s test).
- The first owner-test run failed because the old test expected all reservations to disappear after a snapshot ended; the current live scene deliberately retains a one-byte minimum lease for its empty buffer set. A second new-test attempt used a point for an STL capture and correctly received an unsupported-source error; the fixture was corrected to an authored triangle mesh. Both cases pass afterward.

## Remaining limits

This is not full unique-allocation ownership: tracking starts when the first viewport snapshot is requested, and a replacement scene is not registered until its own first snapshot. Old and new scenes can share some underlying buffer `Arc`s yet have separate leases, causing conservative double counting; lazy picking caches and metadata are still manually estimated. Snapshot failure may leave the current scene's buffer lease registered until scene replacement, intentionally covering the still-live scene. The STL detached capture can count the registered scene buffer conservatively again. Physical free-memory admission also treats the live buffer lease like an outstanding reservation even though those buffers have already been allocated, which can refuse early under physical pressure. Other worker paths, GPU staging and native OCCT allocations remain separate. No full managed-owner gate, process/RSS limit, physical-pressure test, release performance or desktop presentation claim follows.

## Incremental scene follow-up

`update_owned_with_retained_bytes` explicitly clones every existing render-buffer `Arc` into its new scene and may add one new buffer. The Controller now transfers the existing buffer owner to that incrementally updated scene rather than releasing it at publication. At the next viewport snapshot it reserves only previously unregistered buffer bytes plus the small lease-owner allocation. Immutable linked lease owners let older worker snapshots retain their original prefix while newer scenes retain both old and new allocations; their iterative destructor prevents recursive stack growth. New buffer bytes are still covered by the construction reservation until publication and then by caller-held scene accounting until the next viewport registration.

One fixture keeps an old snapshot across an incremental edit and a new snapshot: the registered amount grows by the added buffer, the new snapshot metadata and one small lease owner, not by a second full old buffer. It verifies the live scene keeps the shared lease after old snapshots are released. A 10,000-node synthetic lease-chain test retains the oldest 5,000 while releasing the newer half, then releases the rest without recursive drop. Five presentation owner and five scene-pressure tests pass; after the follow-up, 20 file lifecycle, 11 gesture, nine interactive RAM (six large tests ignored), 44 STL and 27 offscreen GPU tests pass on E: debug with default features, OCCT 8.0.1 and `-j 2`. GPU tests took 53.06 s; the lease-chain test took 0.07 s. The chain-only test was added after the GPU run and changed no production code.

This transfer is justified only for the incremental function's retain-all guarantee. Complete rebuilds, Undo/Redo and other paths can still count shared allocations separately; scenes still get their first registration at the first viewport snapshot, and lazy picking caches remain outside the shared buffer owner. Each incremental buffer registration retains a small, accounted lease node as long as its buffer remains live. Desktop behavior, OS-wide pressure, memory peak and performance remain unmeasured. The earlier limitations above remain applicable except that the tested incremental old/new scene case now shares the old buffer lease.
