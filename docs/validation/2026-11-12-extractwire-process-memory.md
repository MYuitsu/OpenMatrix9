# ExtractWireframe process memory sample

One isolated Windows test process created eight radius-2 mm, height-5 mm OCCT cylinder roots with display deflection 0.01 mm, saved and reopened them, then selected all eight and ran the product controller's `ExtractWireframe` once. It produced 24 curves in 78.854 ms; one Undo restored the original entity set and Redo restored the output set. The command is `cargo test -p om9-app --test wireframe extract_wireframe_reopened_multiple_cylinders_process_memory_probe --target-dir L:/om9-target -j 2 -- --ignored --exact --nocapture --test-threads=1`. This is one batch and eight source objects, not eight independent benchmark runs.

Process counters immediately before/after the command were: private bytes 58,511,360 / 58,511,360; process-lifetime peak pagefile 58,531,840 / 58,531,840; working set 62,197,760 / 65,114,112; process-lifetime peak working set 62,197,760 / 65,114,112 bytes. The working-set high-water increment was 2,916,352 bytes (about 2.78 MiB), and no new private high-water was recorded. The fixture and document comparison clones were already live at the baseline. Peak counters are for the entire process lifetime, can already have peaked during setup, and combine Rust, native and OS allocations. These figures neither isolate OCCT allocations nor bound transient native peak, worst-case memory, or native cost for other geometry; Undo/Redo happen after the post-command snapshot. Runtime is one debug-build observation, not a benchmark distribution.
