# Rhino-inspired viewport sensitivity — 2026-11-01

Standalone OM9 now uses π/600 radians per egui logical point for Perspective orbit instead of 0.01. Pan retains the existing projected viewport span at target depth, which matches the ordinary unmodified-frustum form inferred from Rhino's native code. A Windows wheel notch arrives as one winit/egui Line unit; navigation maps each Line to 40 zoom points, and 40 points now target a span factor of 0.81 (reverse 1/0.81). Fractional point/line input stays proportional; OM9 retains its existing cursor anchor and smoothing. `OM9_NAV_SPEED` continues to control the wheel response duration, not the step size or orbit sensitivity.

Evidence: `cargo test -j 2 -p om9-app --no-default-features --test navigation_drag --test navigation_input --test navigation_precision` passed 12 tests, including 100-point orbit, projected pan for both projections, both wheel directions through egui events and deep-zoom anchor. `cargo test -j 2 -p om9-app --no-default-features --lib navigation::tests` passed 8 tests. `cargo check -j 2 -p om9-app` passed with default features; `tools/public_source_audit.py` returned zero errors. Builds use `CARGO_TARGET_DIR=L:/om9-target`; no-default-features is a developer fallback, not a full product runtime validation.

The coefficient is an approximation from [native analysis](2026-11-01-rhino5-native-navigation-analysis.md), not proof of Matrix9 parity. Rhino uses screen coordinates and OM9 egui logical points; actual DPI, high-resolution wheels, event grouping, special frustums, smoothness and a real desktop comparison remain unverified. Rhino's wheel handler sign-normalizes messages whereas OM9 deliberately preserves proportional fractional and multi-step input. Manual M02 UI acceptance remains open.
