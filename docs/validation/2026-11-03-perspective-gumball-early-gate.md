# Perspective Gumball: early-gate baseline

Scope: current dirty worktree, Windows, default `om9-app` features, external `L:/om9-target`, Cargo `-j 2`. The user-reported visible-but-undraggable Perspective Gumball remains a desktop investigation; this record does not claim it is fixed.

Prior evidence in `2026-11-01-gumball-navigation-refinement.md` identified and corrected one cause of repeatedly invalidated viewport refinement. It did not establish that the user's desktop failure was fully resolved. The current application still constructs its controller with `Limits::default()`, whose aggregate `max_bytes` is 256 MiB; the planned 60% admission integration remains open.

# Picking bounds during transient Gumball preview (2026-11-03)

`Scene` caches a spatial index and object spheres lazily. A red/green test warmed the index, moved a selected line by a transient 1000 mm Gumball preview and queried the displayed location: before the fix the old index omitted the line. `Controller::preview_gumball` and `clear_gumball_preview` now invalidate both caches only when a preview transform actually changes; the next picking query rebuilds them from the displayed transforms. The same test verifies that cancellation restores picking at the original position. All nine `gesture_regressions` and fourteen `osnap_ui` tests passed on the default-feature E: test build. This is a CPU/headless correctness check, not proof of the GPU-published frame or desktop behavior. A pick during every changed preview can rebuild the entire index, so this is a correctness fix with an unmeasured large-scene performance cost; a bounded dynamic/static index strategy remains open. The release desktop executable predates the fix.

An opt-in fixture `preview_picking_bench` measures 40 preview-plus-picking samples over 2,001 point objects after an initial index warm-up. On the default-feature release test build on E: with `-j 2`, the test passed: p50 0.546 ms, p95 0.569 ms, p99/max 0.592 ms, measured with `Instant` around preview update and picking. The sample includes index invalidation/rebuild and actual hit verification; it excludes fixture setup. This single lightweight point fixture measures CPU work only and cannot establish performance on dense B-reps, GPU work, desktop FPS or input-to-display latency. It is not a matched pre-fix versus post-fix comparison.

The same release fixture also tests a shared 3,056-point, 5,968-triangle sphere B-rep with independently placed instances. It verifies that instances share their render buffer and the moving point is actually picked. Before local-bounds reuse, 40 samples measured 200 instances at p50/p95/p99 0.702/0.734/0.749 ms and 2,000 instances at 7.121/7.463/7.576 ms. The 200 and 2,000 runs were separate invocations. The implementation now reuses local bounds for consecutive occurrences with the same immutable buffer, then independently transforms all eight corners for each instance; it retains no new heap cache. The same 2,000-instance release fixture after this change measured p50/p95/p99 0.507/0.522/0.534 ms over 40 samples. These are separate runs on the same machine and fixture, without controlling other system load; the result applies to this favorable consecutive-sharing case, not arbitrary mixed objects or desktop FPS.

Five shared-instance tests, seven world-picking tests, nine gesture tests, fourteen snap UI tests and one app offscreen GPU preview test passed. An initial renderer-only culling test failed to link because its feature combination lacked openNURBS bridge symbols; rerunning with `--features om9-kernel/3dm-brep` passed one offscreen culling test. The GPU tests have bounded scope and are not presentation or 30 FPS measurements.

## Batched press and movement after zoom

An opt-in extension of `OM9_INTERACTION_LOG` records Gumball routing, published/input-basis agreement, navigation state, handle hit and commit alongside the existing raw input and frame records. Records remain on the bounded background log queue and are emitted only when logging is enabled; timestamps are application observations, not display-presentation timestamps. A diagnostic release, hash `B64E6F0485F28EB7AE624306DCA86313B2309AE440F3999B744E3ECF2F009FB6`, started in a separate profile and produced its log. A local bridge in that profile confirmed the test document; subsequent Windows automation returned `GetCursorPos ... Access is denied`, so no diagnostic desktop gesture was collected. This binary predates the code fix described below.

In an offscreen GPU/egui test, after zoom begins, a press and a 15-pixel move arrive in one frame and release in the next. Before the fix the canonical B-rep placement stayed unchanged: egui did not produce a drag-start or drag-stop for that sequence. The trace showed that the displayed input basis changed during the press frame and matched again on release; this is evidence for the test sequence, not proof of the earlier desktop observation's cause. An earlier assertion that capture must exist in the press frame was too early: holding the button an additional frame allowed egui to start the drag, so the actual red regression is the release on the next frame.

The UI retains the press origin with the published view/camera basis. For a sufficiently long press-to-release movement where egui did not produce a drag-stop, it tests the original point against the visible Gumball handles and commits only if the same published input basis still matches. A new press, loss of focus or Escape clears the pending origin. Same-frame click input retrieves its press position from the raw event when egui has already cleared `press_origin`; this was needed to restore two existing selection/point-input tests. The red GPU test now passes, checking canonical Z placement and one Undo; it also verifies a short click, Escape and a drag starting away from the handle do not transform the box. The test uses an in-viewport release and two frames; a press/move/release all in one frame, a fast initial move outside the viewport, broad handle/mode coverage and real desktop behavior remain open.

On the E: default-feature build with `-j 2`, 12 GPU/egui Gumball, 11 gesture, 26 GPU navigation/publication, seven Gumball interaction and 20 snap UI tests passed; the public source audit reported no errors. No post-fix release or desktop run is claimed. The original user-reported issue and desktop interaction gate remain open pending a controlled test on the user's setup.

## Entire Gumball drag batched in one UI frame

An offscreen GPU/egui test uses the same Perspective box and zoom, but delivers primary press, movement and release together in a single frame. It failed before this follow-up: a queued image with a newer camera was published during the press frame, so the captured press and the image available for hit testing no longer matched, and the canonical placement did not change. This is a deterministic synthetic sequence, not proof that the user's earlier desktop gesture had identical timing.

For a captured primary gesture awaiting Gumball recognition, a viewport now retains its previously published image while an already-submitted image is pending, provided the full captured input basis and camera still match current content. It does not retain an image whose document, selection, preview, plane, display mode or target size is stale. A repaint is scheduled; once the gesture is captured or released the pending image can proceed. The first implementation held only the press frame and caused two existing post-zoom drag tests to fail on the next frame; extending the hold through pending capture and release restored them. The new test verifies canonical movement, one Undo, normal clicks and Escape/non-handle starts, and eventual publication of the latest camera. The two-frame version remains a separate test.

On E: with the default features and `-j 2`, all 14 GPU/egui tests passed on the final code, including both batched sequences, stale scene/input tests and the Side View grid pixel test. Before the final repaint scheduling refinement, 11 gesture, 26 GPU navigation/publication, seven Gumball and nine navigation lifecycle tests passed; that refinement changed the retry from immediate to 33 ms. These tests do not establish real monitor presentation, input-to-display latency, a drag whose initial movement ends outside the viewport, or behavior of every handle and modal state. The post-fix release has not been built or tested on the desktop; the original report remains open.

## Fast initial movement outside the viewport

An offscreen GPU/egui regression places the primary press on the Perspective box's Z handle, then moves the pointer outside the viewport before the next frame. It failed before the change: using the last pointer position to decide viewport ownership lost the original press. The UI now recovers the original press position for a selected-object gesture only if that point is inside the pane and its visible UI layer, the window is focused, no viewport menu or popup owns the frame, and the corresponding published input basis is valid. A press starting outside the pane cannot be adopted by that pane. The existing source/camera, Escape and focus guards remain in force.

Both a one-frame press/move/release and a two-frame press/move then release pass. Each compares the full committed placement matrix against an ordinary drag using the same camera and endpoints within `1e-6`, checks one Undo and confirms publication resumes. The fixture also checks short click, Escape, non-handle and outside-viewport press do not move the object. On the E: default-feature build with `-j 2`, 16 GPU/egui tests passed on the final code. Before the final no-press event-scan optimization, 11 gesture, 26 GPU navigation/publication, nine navigation lifecycle, seven Gumball and 20 snap UI tests passed. This covers one Perspective Z handle and an endpoint outside the pane but inside the application window; other handle types, operating-system window exit, overlapping UI cases, physical pointer and post-fix desktop remain unverified.

## Same-layer overlay press

An additional offscreen GPU/egui fixture registers an interactive widget above the Perspective box Z handle **on the same egui layer**, waits for layout, and explicitly verifies that widget is hovered at the press point. A press on it followed by movement into the canvas and release in the same frame previously committed a 3.9698 mm Z translation and added Undo. This is a demonstrated synthetic defect, not evidence that the user's original desktop issue had this cause.

On a new primary press, the viewport now requires the origin to be in its actual interactive canvas and the same visible layer, then inspects egui's last-pass interactive rectangles in paint order. If it cannot identify the canvas rectangle or any later interactive rectangle covers the origin, it does not retain that press for Gumball routing. Last-pass rectangles are the layout basis egui uses for interaction; comparing rectangles rather than IDs is conservative when rectangles coincide or layout changes. This allocates and scans a rectangle list on a primary press; cost on a very large UI has not been measured. The test now leaves the complete placement and Undo unchanged; the separate foreground overlay and normal fast batched drag fixtures remain passing.

Dynamically appearing same-pass controls, all layer transforms, popup transitions, physical pointer behavior and post-fix desktop presentation are not established.
