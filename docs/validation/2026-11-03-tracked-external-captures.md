# Explicit external capture leases

`TransactionCoordinator::capture_tracked_document` now returns a cloneable `CapturedDocument` handle whose inner lease owns the immutable document. The shared external account stores a weak reference to that lease, separately from its existing weak document inventory. When the final handle is dropped, the lease expires even if the world or Undo still owns the same document. Cloned handles share one lease. The existing Arc-returning API remains available for compatibility; it is not made into a tracked lease. The handle exposes a document borrow and a weak-identity comparison for Surface snap rather than handing out a new untracked strong owner.

STL captures and the experimental Surface snap worker now use this handle. Account adoption across controller replacement also carries its weak lease registry, and a replacement account with its own active lease is refused. A core fixture checks handle cloning, adoption, last-handle drop and the important case where the old coordinator still owns the document after the lease expires. Another checks refusal of a replacement with a live capture. On the E: default-feature build with `-j 2`, 251 core unit tests, 23 atomic-transaction tests, 19 B-rep picking tests and 52 STL integration tests passed, including background export and captured documents across New/Open. Public-source audit reported no errors and artifact pruning removed no runs.

This is a foundation, not completed Undo or global RAM accounting. Undo inventory does not yet consult the lease registry, and legacy untracked captures and other owners still exist. Registration of the existing document inventory and the new lease happens in separate lock acquisitions, so use for categorization requires a further atomic admission/publication design and lock-order tests. The lease Arc and registry capacity are not yet included in the shared reservation; expired weak entries are pruned on the next tracked capture. No blanket 60% memory guarantee, safe background UI export, release performance or desktop result follows from these tests. Existing windows and documents were not operated.

## Atomic tracked registration

The tracked path now acquires the document registry and reservation registry in the same order as transaction publication, validates retained owners, and registers the lease before releasing either lock. If lease-vector reservation or retained-owner validation fails, a newly inserted document entry is removed and no lease is returned. A deterministic test hook checks both mutexes are held during the formerly intermediate point; another tightens the managed limit and confirms rejection preserves the coordinator snapshot and leaves neither a new document entry nor an active lease. This tests lock ownership and logical rollback; it is not a scheduled multi-thread stress or a proof for every publication path. Allocated vector capacity can remain after a failed attempt.

On E: default features with `-j 2`, 253 core unit tests, 23 atomic-transaction tests, eight Undo-memory tests, 19 B-rep picking tests and 52 STL integration tests passed. Public-source audit reported no errors and pruning removed no runs. Undo still does not consume these leases; the legacy untracked capture API remains, and lease Arc/vector capacity is not budgeted or fallibly allocated in full. Capture drop and any subsequent Undo attribution, concurrent peer locking, native/transient allocations, UI background export and desktop measurements remain open.

## Concurrent peer reservation

A two-thread fixture pauses tracked capture registration while it holds both account locks, then starts a reservation from a replacement coordinator sharing that account. The peer remains pending until registration is released; it then refuses a simulated 15 MiB reservation under a 16 MiB cap because a real 2 MiB captured document remains live. The peer snapshot and reservation count remain unchanged. After the capture and original coordinator are dropped, the same reservation succeeds. Channels coordinate the phases; the timeout checks that no completion was observed while the locks were held, rather than measuring throughput or guaranteeing scheduler behavior under all conditions.

On E: with `-j 2`, the targeted concurrency fixture and the 254 core unit, 23 atomic-transaction and eight Undo-memory tests passed. Public-source audit reported no errors; artifact pruning removed no runs. This covers one capture versus one peer reservation with a simulated reservation size. Concurrent publication, multiple captures/drop transitions, physical RAM fluctuations, lease-allocation admission and Undo attribution remain open; no production code or desktop session changed in this batch.

## Lease metadata in managed admission

Retained-owner admission now includes the tracked-lease vector's actual capacity and a conservative per-entry allowance for the lease Arc allocation, including expired weak entries until pruning. The allowance uses the pinned Rust profile's Arc representation plus extra machine words; allocator overhead and total process RSS remain outside it. Cloned capture handles share one charged lease allocation. Physical-RAM reservation rechecks conservatively include this metadata alongside pending reservations, so already-materialized bytes may be counted again against the free-memory sample.

When the lease vector must grow, admission first checks an upper reservation for the requested new capacity while the old vector and prospective lease coexist. A separate replacement vector is allocated and its actual logical capacity checked again before swapping; a refused growth keeps the original vector and live leases intact. The registry grows geometrically. The initial preflight uses the requested capacity because an allocator can provide more; the actual-capacity check occurs after allocation, so this is not an allocator-enforced instantaneous peak or an OOM-survival guarantee. `Arc::new` itself remains infallible in this implementation. The pre-existing external-document weak registry can also retain capacity after a refusal; this change does not close that separate accounting/rollback issue.

## Legacy document registry growth

The untracked `capture_retained_document` path now checks the requested weak-registry allocation against the retained-owner budget before allocating, then validates the actual replacement capacity with both old and new vectors accounted before swapping. If either check fails the original registry stays in place. A constrained-budget fixture exercises initial growth refusal, preserved snapshot and capacity, then successful retry after lifting the cap. The fixture does not prove every allocator behavior or concurrent physical-memory change. Expired weak entries are pruned before admission. The tracked-capture path still grows this document registry before admission and needs the equivalent transactional treatment; allocator overhead and peak process RSS are not covered.

On E: using `-j 2`, 264 core unit, 23 atomic transaction, 9 transaction scope, 8 Undo memory and 3 memory-budget tests passed. Public-source audit passed and pruning removed no runs. No release or desktop test was performed.

## Tracked document and lease registry growth

Tracked capture now preflights document and lease vector replacement together, including both old allocations and requested replacements. Each actual capacity is rechecked before publication; the two registries are updated only after admission succeeds under the existing shared lock order. An initial-growth refusal fixture checks both capacities and the world snapshot remain unchanged and a later retry succeeds. Existing tests also exercise lease growth refusal, ownership, shared-account contention and capture lifetime. The fixture does not inject allocator over-allocation or failure at every individual allocation. Arc allocation remains infallible, allocator overhead is excluded, and this accounting is not an OS-enforced peak limit.
