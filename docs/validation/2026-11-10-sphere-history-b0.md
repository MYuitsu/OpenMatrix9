# B0 Sphere history measurement — partial profiles, decision to defer (2026-11-11)

This is a partial B0 batch, not the decision gate. The diagnostic in `crates/om9-app/tests/sphere_history_measurement.rs` creates radius 5 mm Spheres using `Controller::submit("Sphere 5")`, deletes each via `Controller::delete_objects`, and keeps only weak liveness witnesses plus scalar sizes. No external strong display or document snapshot is retained by the diagnostic. The current product path fixes `creation::DEFAULT_DEFLECTION_MM` to 0.01; no product control for a second document-display profile was found. A scene-only remesh must not be presented as a second document/history profile.

The separate correctness fixture `cargo test -p om9-app --test sphere_history_correctness -j 2 --target-dir L:/om9-target` passed: one product Sphere radius 5 mm has analytic volume, and delete → Undo → Redo → Undo retains its source, topology IDs, placement and expected object identity. Undo currently restores the same retained display allocation; this specifically does not demonstrate source-only restoration or eviction.

The focused owner test `cargo test -p om9-app --lib sphere_delete_undo_finds_history_proof_after_optional_cache_drop -j 2 --target-dir L:/om9-target` also passed: for one product Sphere, after dropping the optional cache and deleting the object, history kept the proof alive; after Undo the proof could be found and rebound to the restored object. This does not prove all 32/128 entries retain proofs, nor does it implement an eviction or source-only representation.

Debug build, `cargo test -p om9-app --test sphere_history_measurement -j 2 --target-dir L:/om9-target -- --ignored --nocapture`, default limits and Undo policy, Windows machine with 68,635,316,224 bytes physical RAM. The 32-Sphere workload completed: 64 Undo steps; 32 display owners still live after all deletions; display allocation bytes 4,552,832; source text payload 28,512 bytes; `undo_memory_bytes()` 7,450,784; maximum of post-action samples of retained usage plus scene usage 10,692,500 bytes; first Undo 816.219 ms. Weak witness headers and measurement code are diagnostic overhead. The post-action maximum is not the transient/native peak. Source text is payload only, not the full source/topology/proof/metadata cost. The 128-Sphere case was still running when this partial record was written.

The same run subsequently completed successfully: the 128-Sphere workload retained 256 Undo steps and 128 live display witnesses after deletion. Their summed display allocation sizes were 18,211,328 bytes (17.37 MiB); source text payload 114,048 bytes; `undo_memory_bytes()` 47,032,288 bytes; maximum sampled retained plus scene usage 52,530,664 bytes; first Undo 100,678.041 ms. The entire two-workload debug test took 12,427.76 seconds. These are debug-build observations, not release or desktop latency, and the sampled maximum excludes transient/native peaks. The weak witnesses are non-owning; display sizes are summed without explicit deduplication, so the sum is a gross upper bound if allocations alias, not a proven unique eligible-byte count.

The 128 result's gross upper bound is about 38.72% of measured history bytes but below the required 32 MiB even before cold-record cost; the 32 result is also below 32 MiB. Therefore neither measured fine-profile workload can meet both selection thresholds through reclaiming these display buffers. Cold-record overhead, proof eligibility, external pins and actual eviction remain unmeasured. A second product history profile, native peak, desktop latency and B1–B3 remain unproved.

Separate kernel-only size check: `cargo test -p om9-app --test sphere_profile_ceiling -j 2 --target-dir L:/om9-target -- --nocapture` passed for the same radius-5 source and analytic volume at deflections 0.1 and 0.01 mm. Display allocations were respectively 25,384 and 142,276 bytes (468/2,570 points; 868/5,008 triangles). Multiplying by 128 independent displays of those measured exact sizes gives 3,249,152 and 18,211,328 bytes before any cold-record cost. This is an illustrative upper bound **conditional on all 128 product displays having the same allocations as each fixture**; it is not the product 128-object history result, proof of the missing product coarse profile, or a B0 decision. The 32-object product sum happens to equal 32 times the fine-profile fixture size.

The fixture now uses `primitive_with_topology`, matching the proof-producing constructor used by product Sphere. Each profile produced 891 bytes of source text and 528 bytes of topology-attestation storage. Complete source/topology/display `storage_usage` was 26,555 bytes at 0.1 mm and 143,447 at 0.01 mm. These figures exclude document/history metadata, proof owner and reservation overhead, and do not demonstrate that every history entry retains a usable proof.

The conditional owner/caller map for a possible history-only representation is recorded in `implementation/design/M01/viewport-export-separation-20261102/B0_HISTORY_OWNER_MAP.md`. It identifies the participant-equality and full `Arc<Document>` constraints; it is not a claim that the proposed record is implemented or that its costs meet B0.

**Decision:** defer B1–B3 for this batch: neither measured product workload at the available fine profile can meet the 32 MiB threshold, and the second product profile and complete costs were not measurable. This is not B implementation or an exhaustive B0 measurement, and it does not prove that other workloads or profiles cannot benefit. The conditional owner/caller map remains design material for a future separately justified attempt.

On 2026-11-11 a targeted attempt to sample CPU stacks for the unexpectedly long live debug workload failed: `wpr -start CPU -filemode` returned `0xc5585011` because Windows did not enable its profiling policy. `wpr -status` confirmed no recording remained active. No CPU trace was obtained; the exact hot path and remaining time therefore remain unknown. The original workload was not restarted.

Subsequently, a small user-mode diagnostic (`implementation/design/M01/viewport-export-separation-20261102/b0-sample-position.cpp`) sampled the instruction pointer of threads in the agent-owned synthetic test process eight times. It briefly suspends each thread only while obtaining its instruction pointer, resumes it before resolving symbols, and is not a statistical CPU profile or a stack trace. Two active-thread samples resolved inside `retained_document_storage` closures, one to `retained_breps`, and the rest to BTree iteration helpers. In current code `retained_document_storage` scans preceding retained documents for matching B-rep allocation owners; the production call is reached from the allocation-free fallback after indexed admission cannot be used. This is direct evidence that the fallback was executing during those samples, not proof of why indexed admission failed, its share of total runtime, or an infinite loop. The short suspensions are a measurement perturbation; no code or live history was changed by sampling. The original workload remained running afterwards.

Static follow-up: the indexed path first admits a duplicate-inclusive upper bound across the current document and every Undo/Redo before/after document; `storage_usage_upper` counts each B-rep display even when its allocation is shared across document versions. With the default 256 MiB byte limit and the measured 142,276-byte fixture display, a hypothetical single copy of each successive 1..61-Sphere document already totals 269,043,916 display bytes before metadata. This illustrates why the conservative bound can force the allocation-free fallback despite far smaller deduplicated retained data. It does not establish the precise limit or branch that triggered the observed fallback in the running process; other counters and validation can also trigger it. No admission logic was changed.
