# Rhino 5 native navigation analysis — 2026-11-01

Scope: static analysis of the locally registered Rhino 5 decompilation, not a runtime comparison or proof of Matrix9 parity. Addresses below identify functions in that particular x64 export. The decompiler warns that type propagation fails in `Magnify`; floating-point arguments in other bodies may also be incomplete. No original source is reproduced here.

- `CRhinoAppViewSettings::Defaults` (RVA `0x1fbc00`) initializes offset `0x10` to IEEE-754 0.9. `CRhinoAppViewSettings_GetSetDouble` identifies index 1 with this offset, and RhinoCommon names index 1 `ZoomScale`. Profiles may override the factory value.
- `CRhinoAppSettings::ViewSettings` places the view settings at offset `0x228`; `OnMouseWheel` (RVA `0x43ef70`) reads offset `0x238`, hence the same zoom scale. For a nonzero wheel message it reduces delta to its sign and passes `1 / scale²` for positive, `scale²` for negative to `MouseOrGestureViewZoom`. At 0.9 these are approximately 1.2345679 and 0.81. Magnify (RVA `0x44a860`) divides orthographic frustum dimensions by its factor, so positive input yields span 0.81 and negative yields 1/0.81. It accepts the cursor anchor; perspective follows a camera movement path with additional guards. Multiple wheel detents packed in one message are sign-normalized in this function. No claim about driver event delivery or actual runtime smoothness.
- `MouseRotateView` (RVA `0x4476f0`) uses horizontal and vertical mouse-point differences times a global speed, then angles `-delta * speed * pi / 600`, with world-up or camera-up and camera-X axes, subject to locks and special projection/target paths. `SetViewSpeed` command text identifies 1.0 as its default; static data initialization for that global has not independently been verified. Assuming that default, 100 coordinate units corresponds to 30 degrees per axis before the other branches. The coordinate units and DPI behavior need runtime verification.
- `MouseLateralDolly` (RVA `0x4495d0`) uses screen port, frustum, camera axes and a screen-to-view transform to construct camera translation. Decompiler lost floating-point arguments in vector operations, so an exact scalar formula and perspective depth cannot yet be reconstructed reliably. It does not justify assigning an independent numeric pan sensitivity.
- `MouseRotateCamera` is a distinct mode: its angular denominator is the larger screen-port dimension, not 600. `MouseMagnify` is a different drag mode and must not be confused with wheel zoom. Wheel `ZoomScale` and `SetViewSpeed` are separate controls.

Next: inspect matching native instructions or the original binary for the missing pan operands and global initializer, then measure both applications using matching viewport size, projection, initial camera, Windows scaling and controlled wheel/drag events. Validate camera poses and delivered event counts; preserve the original private references. No OM9 implementation was changed.

## Machine-code follow-up

The installed x64 Rhino 5.14.00522.08390 executable has SHA-256 `8daacaa0a9a7ade3c82793309fdff421306b736fa57bf1342b01369d0f14089b`. Disassembly at RVA `0x4495d0` agrees with the decompiled function's structure and resolves omitted SSE operands. The PE image data initializes the view-speed global at RVA `0x1583550` to `1.0` and the other multiplier at RVA `0x10e8298` to `0.5`. This is the installed binary's initial value; a command or profile/runtime state may differ.

Let `q0` and `q1` be the transformed start and end screen points produced by the function's screen-to-clip transform followed by the inverse clip modifier; let `s` be view speed, and let `l,r,b,t` be frustum bounds. The native scalar terms are `x = (q1.x-q0.x)*0.5*s*(r-l)` and `y = (q1.y-q0.y)*0.5*s*(t-b)`. In perspective both are multiplied by `target_distance / near_distance`. The camera is translated by `-(x*camera_X + y*camera_Y)`, and the target is recomputed using the same target distance and camera Z. Lock, validity, special clip transforms and target correction remain relevant. With ordinary unmodified clip transforms this corresponds to scaling the screen drag by the projected frustum dimensions at target depth; exact direction follows Rhino's screen transform. This establishes the missing native operations, not measured parity with OM9.
