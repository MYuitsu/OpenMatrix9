# STL worker requires sampled reservation

The shared external reservation API permits a reservation without a physical RAM sample for already-owned or other accounted uses. The STL worker previously accepted such a reservation for new export work. A red fixture showed that it started with an unsampled export reservation. The reservation guard now records whether its own admission included a valid physical sample; the STL worker requires this after acquiring the existing single-worker permit. On refusal both permit and reservation are dropped, and the destination is not modified. A currently busy export continues to report its existing busy error first. The source document and Undo remain unchanged.

On the E: default-feature build with `-j 2`, 31 retained-owner/core tests, four STL background-job tests and 14 cancellation/admission tests passed. The new test verifies rejection, destination preservation and release of both resources; the existing sampled worker fixture still succeeds. The pre-fix test's specifically identified temporary file was removed. Public-source audit was run separately.

This flag alone is only a necessary condition: the caller supplies a point-in-time sample and its requested reservation size. The subsequent launch-time recheck below improves freshness, but cannot prove the reservation sufficient. OCCT transient peaks, actual aggregate memory of all owners and UI integration remain unbounded/unimplemented; synchronous export has its own existing path. No claim of process RSS control, complete 60% enforcement, safe operation under arbitrary memory pressure, or desktop acceptance follows from the sample flag. The interactive 256 MiB limit remains open.

## Launch-time physical RAM recheck

Before spawning the STL worker, OM9 now requests a fresh physical-memory sample from the platform and rechecks free headroom against all currently outstanding external reservations while holding their shared registry lock. It also rejects a lower total physical capacity or a shared managed ceiling tightened since this reservation was admitted, requiring fresh admission rather than assuming previously counted owners still fit. If the sample is unavailable or insufficient, the worker is not started and the reservation and permit are released. On unsupported platforms where the current memory provider returns no sample, this background path explicitly refuses rather than inventing a value.

A deterministic core test covers free-memory decline, a concurrent reservation, release of that reservation, lower total, invalid samples and tightened shared policy; it preserves the coordinator snapshot. A worker-level fixture injects low or unavailable launch samples and checks unchanged destination, document, reservation count and worker permit. The actual Windows-sample background worker fixture also passed. On E: with default features and `-j 2`, 32 core retained-owner tests, 15 worker cancellation/admission unit tests and four background-job integration tests passed.

The OS sample remains a snapshot: another process can consume RAM immediately afterwards, reservations are deliberately subtracted conservatively even if some memory is already materialized, and other OM9 owners and native transient peaks are not fully accounted. The caller's requested bytes are still not proved sufficient, synchronous/UI export is not wired through this worker, and the 60%/256 MiB project gates remain open. This is not a process-RSS guarantee.

## Authored-mesh allocation lower bound

Before refreshing the launch sample, the worker now totals a known lower bound for authored mesh arrays in the immutable selection, expanding each block occurrence independently: three `f64` coordinates per input vertex, at least one three-`u32` triangle per validated mesh face, and one source flag per face. A reservation smaller than that minimum is refused before the worker starts. Arithmetic is checked. A red/green fixture showed that a sampled one-byte reservation previously launched an authored-mesh export; it now refuses without changing the target and releases its reservation. Another fixture verifies that two instances of a shared mesh are counted twice. Seventeen cancellation/admission unit tests and four worker integration tests passed on E: with default features and `-j 2`.

This is explicitly a **lower bound**, not a sufficient estimate: quads create two triangles, capacities can exceed lengths, and B-rep/NURBS/native tessellation, topology maps, snapshots, encoding, worker state and native peaks are excluded. A B-rep-only selection has a zero known authored-mesh bound. Passing this check therefore does not authorize connecting the worker to UI as a budget-safe solution or establish the 60% gate. The readiness traversal and bound calculation also remain synchronous and have not been timed on huge nested scenes.

## Topology-array floor and quads

The authored-mesh lower bound now counts the actual number of triangles implied by valid triangles and quads, including each block occurrence. It covers the output positions and triangle indices that coexist during topology analysis, plus one `usize` parent and one `u8` rank per authored output triangle. Source flags are no longer added to this same phase: they are dropped when soup construction returns, before topology arrays are allocated. The prior floor could admit exactly the old soup/flag estimate even though it could not hold these mandatory topology arrays; a red/green worker test confirms rejection before spawning, release of the reservation and preservation of destination bytes. Separate tests cover two shared instances and both triangles of a quad.

On E: default features, `-j 2`, 22 STL session unit tests and four background-job integration tests passed; public-source audit reported no errors and artifact pruning removed no runs. This is still a necessary minimum, not an upper bound or safe production reservation: it excludes hash-table storage and capacities, B-rep/NURBS/native tessellation and scratch, writer buffers and indexes, worker overhead and aggregate owners. For a B-rep-only capture the authored-mesh part remains zero. It does not authorize UI worker integration or prove the 60% RAM gate. The extra face traversal is synchronous and its latency on a large nested selection has not been measured.

## Native adapter ceiling from worker reservation

An experimental background worker previously forwarded the capture's original `Limits.max_bytes` to OCCT even if its own reservation was smaller. A box fixture with a sampled reservation slightly larger than its source string reproduced successful export before the fix. The worker now clamps its captured byte limit to the reservation before starting, so the B-rep snapshot adapter refuses that fixture. The target remains unchanged and the worker and selection reservations are released. The kernel currently reports this particular snapshot refusal through an I/O-wrapped error; it is not yet a dedicated typed budget diagnostic.

This cap is a necessary per-snapshot constraint, not a bound on the simultaneous soup, topology maps, other Rust allocations or native OCCT mesher transients. It does not change the synchronous UI export path, establish complete admission or authorize wiring the background worker to UI.

On the external E: target with `-j 2` and default native features, the new fixture failed before the clamp because the worker exported successfully. After the clamp, it reports the existing `BRep snapshot bytes` refusal and leaves the target unchanged. All 26 STL session tests and 60 serial STL integration tests passed, including a background export with a larger reservation. The first green run exposed an overly narrow test assertion expecting the word `budget`; the assertion was corrected to match the actual adapter error before the successful rerun.
