# Small trim-hole display witness

An authored planar B-rep contains a square 0.004 mm hole, while the selected face display is deliberately corrupted with one large triangle crossing its center. The previous perimeter-based allowance accepted this display and started ExtractIsocurve after a simulated face pick at the hole; the regression failed twice before the fix. The 0.004 mm hole is far larger than the 0.000001 mm verification tolerance. The document and an existing Redo are captured before the command.

The existing OCCT bridge now tests an additional witness: for a hole bounding box intersecting a displayed triangle, its center is projected to the plane; when strictly inside that triangle, it is checked against the trimmed source face using the existing distance verification. The malformed fixture is refused and preserves the document and Redo. A separately generated valid display of the same small hole remains usable for ExtractIsocurve and passes Undo/Redo. This is a witness, not a general hole-containment proof: a concave or irregular hole may not contain its bounding-box center, a narrow intersection may miss the center, and finite precision, the existing outside-area allowance, non-planar faces, physical RAM exhaustion and desktop remain limitations. OCCT remains confined to the existing selected geometry adapter; Rust retains session and transaction ownership.

Verification used the existing `L:/om9-target-surface` tree with `-j 2`, because the user's prepared desktop window was running from `L:/om9-target`. The focused two small-hole tests passed; the full ExtractIsocurve integration suite passed 52 with 3 ignored; Solid workflows passed 118 with 1 ignored. `brep_picking_precision` passed 19 and failed 1: `indexed_face_refinement_respects_a_trimmed_through_hole` rejected a display with the existing `triangle crosses trim boundary` error. Temporarily disabling the new witness and rebuilding the same target still reproduced that failure, so it was already present in current source; an older executable in the other target passed and is not proof for the current source. The witness was restored and the final Isocurve suite was rerun. The failing existing regression remains open and the group must not be reported as fully passing.

No claim is made that real imported files naturally contain this corrupted display, that all invalid displays are caught, or that native peak memory has been bounded. The existing running application was not replaced or restarted. The debug application in the second target was built by Cargo's integration-test workflow; it has not been tested on desktop with this fix.

## Existing circular-hole display refusal

An instrumented run of the existing `indexed_face_refinement_respects_a_trimmed_through_hole` test identified a naturally generated display triangle, not the deliberately corrupted small-hole fixture, as the cause of its failure. Its two boundary vertices lie on the radius-2 circular hole at approximately `[-1.24697960,-1.56366296,10]` and `[-1.46610374,-1.36034548,10]`; the edge joining them is a straight display chord. Its third vertex is `[-5,-5,10]`. The OCCT cut measured about 0.00111477 mm² outside the source face, above the current 0.00004184 mm² threshold, while display deflection is 0.2 mm. This establishes why that authored solid's normal display is rejected; it does not establish behavior for arbitrary circular holes, imported drawings, or desktop. The temporary native diagnostic print was removed after the observation.

The same test failed after disabling the new small-hole witness, so this refusal predates that witness in the current source. Simply increasing the area allowance would risk accepting a click in a hole. The current `SelectedSubobject` retains source identity but discards the hit world point; a safe route must preserve or re-resolve the actual pick against the trimmed source, bind it to the current scene/camera/selection, and handle preselected or numeric faces without an invented point. It must still reject an actual click in the hole and preserve document and Redo on failure. The circular-hole test remains failing and no product behavior was loosened.

### Candidate product path, pending consent

The existing NativeBrep isocurve path already retains a viewport ray and checks session, selection and source before resolving a source intersection. It cannot simply be reused unchanged for an editable B-rep: `isocurve_ray_face` currently chooses the intersection nearest the display reference within a pixel-derived distance, so a different nearby source face could win. A B-rep version must additionally bind the resolved source face to a witness for the displayed selected face in the **same source read**, and must repeat or preserve an equivalent binding through execution. It must reject ambiguous, stale, out-of-screen and hole hits, and maintain selection/session/scene/placement and resource admission checks. Face selections made by number or without a stored viewport hit remain on the current conservative path. This is a design candidate only; no new behavior has been enabled. User consent is pending because using the verified point in place of rejecting every imperfect triangle changes the previously approved refusal rule.

The final, non-instrumented small-hole source was rebuilt in the existing second target and the two focused small-hole tests passed again. The circular-hole regression above remains open; no desktop or native-peak claim follows from these tests.

## Surface Snap product-path distinction

The existing `indexed_face_refinement_respects_a_trimmed_through_hole` test combines a direct whole-display verification assertion with later Surface Snap checks. To determine whether the first failure masked a separate product failure, one diagnostic run temporarily asserted the known conservative rejection instead; the remaining checks passed. The original assertion was then restored, so the original regression is still failing and has not been relabeled as fixed.

A separate permanent focused test now exercises the Surface Snap controller path on the authored drilled block without relying on that whole-display assertion. It refines a material candidate to `[3,1,10]` within 1e-6 mm and rejects an adversarial copy whose cursor is moved to the center of the hole. One execution passed. The altered candidate tests a mismatch/refusal, not a physical click into the hole or a proof of all snap paths. The test uses the current OCCT debug build; physical desktop, actual OOM and general geometry remain unverified. No product behavior changed in this follow-up.
