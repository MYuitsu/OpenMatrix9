# Top 11 polycurve cut parameter (2026-10-30)

Standalone Rust OM9 on Windows; base commit `89ef2676b597ebc5ab38fa5c6acf0ad47a2f261b` with working-tree changes. Polycurve evaluation and split use equal parameter intervals per segment, but `trim_curve` used cumulative arc length and even assumed each segment's local fraction was proportional to length. Split/Trim by cutter supplies evaluator fractions to `trim_curve`, so an unequal-segment target produced pieces at the wrong location.

The core regression used lengths 1 and 10: Top 11 interpreted evaluator fractions 0.2..0.4 as length fractions and produced endpoints 2.2 and 4.4 rather than 0.4 and 0.8 before the fix. The new `trim_curve_by_parameter` intersects each segment's uniform parameter interval and uses its own split operation. Top 11 calls it for intersection fractions; the existing `trim_curve` retains its historical arc-length behavior for other callers. The test covers both contracts, forward and reversed curves, and four interval arrangements; another checks endpoints of an arc/line polycurve in both directions. Controller tests split and trim an unequal polycurve at a real cutter and verify endpoint geometry, Undo and Redo.

With `CARGO_TARGET_DIR=L:\om9-target` and `-j 2`, four core curve/Top 11 suites passed 52 tests and the Top 11 application, options and BRep suites passed 56 tests on the final implementation; the added arc/line core case passed in an 11-test curve suite. A complete core run passed 914 tests with 2 ignored on the earlier implementation before separation of the two contracts. Public-source audit passed. This proves the tested open polycurves, not arbitrary NURBS, closed curves, all placements or the OS-level UI. Split Point still supports only one straight line; full Top 11 and human M03-UI acceptance remain open.
