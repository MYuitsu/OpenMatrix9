# Top 11 Trim: multiple curve targets (2026-10-30)

Standalone Rust OM9 on Windows, base `89ef2676b597ebc5ab38fa5c6acf0ad47a2f261b` plus working-tree changes. Multiple selected curves previously failed with `split/trim need exactly one curve`; the new controller regression first failed on that error.

Trim accepts multiple curve targets selected before or after invocation, accumulates cutters, and prepares intersections for targets hit by at least one cutter. Unhit targets remain unchanged. Each selected portion commits immediately as its own Undo transaction; Enter finishes, and Cancel ends the command without undoing already committed portions. This is an OM9 interaction decision, not a claim of original Matrix parity. The initial batch removed a target from the pending list after its first trim; [the follow-up](2026-10-30-top11-trim-continuity-repeat.md) supports another pick on surviving pieces with interior cutter intersections.

For typed coordinates, the owner finds targets within document tolerance and rejects points matching more than one target. In the viewport, the scene hit-test uses pixel tolerance and supplies the explicit target and hit point to the same trim owner, avoiding a world-distance/pixel-distance mismatch and ambiguous target choice. Tests cover two targets, an unhit target, independently hitting cutters, a far pick, ambiguous intersecting targets, an explicit hit, selection after CMD invocation, cutter removal/reselection, Cancel, geometry and Undo/Redo. One simulated egui test clicks a viewport and checks which curve changed and Undo; it does not establish OS mouse input, GPU display or human M03-UI acceptance.

With `CARGO_TARGET_DIR=L:\om9-target`, `-j 2`: app Top 11/options/OCCT BRep suites passed 72 tests; no-default-feature Top 11/options passed 57; the focused egui viewport test passed. Public-source audit passed. Numerical cutter/projection limits, surface/BRep targets, target selection highlighting after each commit, actual desktop interaction and full Top 11 remain open. The documented Matrix interaction requires selected objects to cut one another rather than this implementation's separate target/cutter stages; see the follow-up.
