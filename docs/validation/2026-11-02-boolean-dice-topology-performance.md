# Boolean operand validation: dice MCP timing

2026-11-02, Windows x64, local OCCT 8.0.1, unoptimized debug binaries, MCP stdio. The fixture is `tools/dice_21_no_undo_benchmark.py`: 20 mm box, 21 radius-1.5 mm sphere subtractions, Boolean2Objects Difference, DeleteInput=Yes, benchmark-only Undo disabled. All 21 cuts succeeded and each resulting document had one object. Times run from MCP startup to successful `.om9` save; the cavity time includes sphere creation, selection, preview, commit and state calls.

| Run | Startup through save | Final cavity |
| --- | ---: | ---: |
| Prior reference, separate run/build | 120.182 s | 10.943 s |
| Local comparison baseline | 49.929 s | 4.077 s |
| Single Build and topology-only operand check | 42.002 s | 3.696 s |

The local comparison is one run per build, not a controlled repeated benchmark; system load and binary revisions can differ. The single-Build-only exploratory run took 56.435 s and its final cavity 3.822 s, with overlapping kernel tests, so no independent speedup is established for that change. MCP server logs on the final cavity measured Difference preview 2185 ms baseline vs 1506 ms modified, and Enter/commit 1189 ms vs 1340 ms; these measurements are not a CPU profile. Normal Undo and release/desktop latency remain unmeasured. The prior 120 s debug benchmark is not a controlled before/after comparison.

Before this change `editing::boolean` called the complete exact measurement service for both operands, including high-precision area, volume and optimal bounds, merely to check for solids. The Rust adapter still checks retained BRep integrity and budgets; native `read_shape` still checks OCCT validity and the same solid-map existence check is performed on the already-read shape. Output snapshot validity and budget checks remain in force. The surface trim/intersection entry points retain their existing detailed input checks. Boolean builders now use empty construction, explicit argument/tool lists and one Build; no claim is made that this alone explains the measured change. Measurement-integral failure no longer rejects an otherwise valid solid merely while testing Boolean eligibility.

All three runs produced native BRep SHA-256 `22ce14cab9bf89e8e5b5a45b806ce1196f8d44b2b16bec5645a0ba4f3783a23f`; baseline and modified display points, triangle indices, segment indices and face-edge topology match. Per-session subobject IDs differ. This is fixture-specific equivalence, not a proof for every model or an independent print/manifold certification. Retained baseline and modified timing receipts: `2026-11-02-dice-boolean-baseline-timing.jsonl`, `2026-11-02-dice-boolean-topology-timing.jsonl`. Baseline debug executable SHA-256 `8ee341dd4e1583d0484bba499012f35cd26c2a8cbe49e4467bccbe4ff148afce`; modified `7fb12f9f758f11b878fe8345123ec45bed3cc06e54e5ccdd77b7ba8d189f95bf`.

Validation: `cargo test -j 2 -p om9-kernel --features 3dm-brep --test l2_01_10`: 70 passed, including numeric Union/Difference/Intersection, empty result, disjoint tools, tampered inputs, open shell and surface trim. App `mcp_stdio`: 3 passed; `solid_workflows`: 113 passed, one native UI test ignored. Public-source audit: zero errors. The normal debug executable was locked by another process; the linked executable under `debug/deps` was copied to a separate name for the modified run. Existing running windows and their documents were not closed. Further investigation should profile normal Undo retention and commit, run repeated matched builds, and measure release end-to-end before making broad performance claims.
