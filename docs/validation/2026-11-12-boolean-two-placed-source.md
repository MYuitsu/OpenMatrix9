# Boolean Two Objects: translated B-rep source

The product Controller fixture `boolean_two_reopened_sphere_profiles_have_same_analytic_results` uses a radius-3 mm sphere centered at the origin and a 4 × 8 × 8 mm box placed from x=0 to x=4, y/z=−4 to 4. Each input's source-world bounds are asserted after OM9 v4 save/reopen. The sphere is tessellated from the same source at 0.5 and 0.01 mm; the test verifies distinct triangle counts. A second pair of cases uses a rotated box occupying the same world bounds. Menu dispatcher and CMD routes are exercised.

Before the fix, with the box translated through `transform_brep`, Union returned volume 256 mm³ instead of 256 + 18π mm³, sphere-minus-box was reported empty instead of 18π mm³, and Intersection measured approximately 55.813 instead of 18π mm³. The same sphere and a box constructed directly in its world position gave the expected values in the adapter. Disabling the Boolean OBB optimization did not correct the fixture and that trial was reverted. These observations isolate this fixture's failure to the transformed-box path; they do not establish the cause of every affine Boolean failure.

The native transform adapter now uses OCCT's rigid `BRepBuilderAPI_Transform` with `gp_Trsf` for matrices whose linear portion is exactly identity, retaining the existing general affine path for all others. With this change the fixture passed all five Boolean preview volumes against analytic values at both profiles for translated and rotated boxes. It checks no document mutation during previews, one transaction for the final Union and exact document Undo/Redo. The separate existing late-invalid-input and stale-preview cases exercise refusal semantics. This is not a proof for arbitrary geometry, affine transforms, imported models, peak native allocations or native desktop interaction.

An existing kernel test expected a translated cylindrical face to lose its analytic cylinder and be refused by the Boss carrier. After the fix it retains that surface: the test now checks radius, volume and source-world bounds of the translated carrier. The kernel transform suite passed 11/11; the Boolean kernel suite passed 75/75 with `--features 3dm-brep`; app Solid controller regressions passed 75/75, Solid workflows 114 passed/1 native UI fixture ignored, and Solid integration 198 passed/1 ignored. The first kernel transform invocation without the required `3dm-brep` feature failed to link; the correctly configured run passed. Debug executable build and public source audit passed. The user-facing skill wording awaits separate approval.

## Non-rigid placement: failure and temporary refusal

A follow-up of the same fixture replaced the translated box by a 2 × 8 × 8 mm box with x-scale 2 and the same resulting world bounds. Before the safeguard, Union again returned 256 mm³ instead of 256 + 18π mm³. Removing ShapeFix for positive determinant and forcing `BRepLib::SameParameter` did not correct this case; both experiments were reverted. The general affine adapter remains unchanged and a complete native fix is still required.

The product Solid Boolean source paths now refuse placements whose linear part is not a proper rigid transform, including scale, shear and reflection, before transforming that source or publishing a Boolean result. This is a conservative temporary loss of functionality, not affine support. The reopened scaled fixture is refused at both display profiles without preview and preserves document and Redo. `boolean_rejects_nonrigid_placements_without_losing_redo` separately checks scale and reflection in Boolean Union and Boolean Two Objects; the original translated and rotated fixtures still pass. Solid controller regressions passed 76/76; Solid workflows 114 passed/1 ignored and Solid integration 198 passed/1 ignored. Debug build and public source audit passed.

The guard examines the current object placement only. It does **not** establish correctness for affine changes already baked into B-rep source, direct kernel callers, other product consumers, arbitrary rigid transforms or imported geometry. Such paths and complete affine support remain open. ### Direct kernel diagnosis

A focused kernel reproducer, `boolean_nonuniformly_scaled_box_matches_analytic_sphere_union`, remains explicitly ignored because it fails and bypasses the product placement guard. In its 0.01 mm configuration the union returned an invalid snapshot error, `BRep face has no tessellation`. Temporary native diagnostics observed that OCCT classified x=−5, −1 and 5 outside and x=1 inside the scaled box, with the infinite point outside; all six box faces were BSpline surfaces. Before snapshot tessellation, the raw union had seven faces and its measured volume was 256 mm³ rather than 256 + 18π mm³. These point samples rule out a simple globally inverted solid in this fixture, but do not prove all face parameterizations or why OCCT's Boolean produced the wrong result. Temporary logging was removed.

OCCT's local `ShapeCustom_Surface` header describes approximate conversion to analytic surfaces and warns that parameter laws change; using it without a proof of exact geometry and matching pcurves would not establish this plan's CAD accuracy. No such approximation was added. The configured kernel Boolean suite passed 75 tests with this one reproducer ignored. Current git objects: `editing_bridge.cpp` 9d583543d70a430efa391a0973ed7f8281b91aac; `transform_bridge.cpp` 95a4e97726031b50195ad01fe8adfe66481bcac0; `l2_01_10.rs` e554c0d014986a26f6d1cd320f2073345b3729a2. The non-rigid product guard and all its stated limitations remain in effect.

Further temporary diagnostics found finite, ordinary face parameter intervals (ranges within −8 to 8), so unbounded parameter domains are not established as the cause. OCCT `BRepAlgoAPI_Check` considered the transformed box and the input pair valid. It marked the raw Union result invalid when both small-edge and self-interference checks were enabled, at output deflections 0.5 and 0.01 mm; with small-edge checking disabled, self-interference alone reported valid. The 0.5 result was emitted with the wrong 256 mm³ volume; the 0.01 result failed snapshot tessellation. This is a promising diagnostic for these cases, not proof that checking catches all incorrect Boolean results. The [OCCT 8.0.1 API](https://occt3d.com/dev/doc/refman/html/class_b_rep_algo_a_p_i___check.html) documents these checks as independently configurable. No global check was added: its native memory/time cost and potential rejection of valid small CAD features have not been characterized or admitted. Temporary diagnostics were removed; after removal, the kernel Boolean suite passed 75 tests with the known reproducer ignored.

Additional temporary trials at the actual Boolean operation tested fuzzy values of 1e-7, 1e-5 and 1e-3; all retained the 0.01 mm fixture's `BRep face has no tessellation` failure. A temporary result check at the Boolean operation rejected that fixture before snapshot creation. With this check enabled the sequential kernel suite passed 77 tests, with the known reproducer ignored, in 15.97 seconds; one sequential no-check run took 14.89 seconds. These single runs are not a controlled performance study and do not measure peak native memory or prove that valid small features are accepted. An earlier timing accidentally instrumented plane trim and is excluded. Neither experimental change was retained; after removal the kernel suite again passed 77 tests with one ignored. The underlying affine failure and risk for sources whose affine transform is already baked remain open.

### Baked-source publication guard

A controller regression saved and reopened a sphere and a box whose nonuniform scale was already baked into its source. With identity placement, Boolean Union previously committed 256 mm³ at display profile 0.5 instead of the analytic 256 + 18π mm³. The normal product Boolean path now asks OCCT to check the nonempty result for small edges and self-interference before publication. In this fixture it refuses at profiles 0.5 and 0.01, retaining the document and Redo. The check is conservative: it does not correct the geometry or prove other results correct. A valid 0.001 mm box protrusion passed one checked kernel fixture; arbitrary small details and false rejections remain uncharacterized.

Applying the check to all kernel Boolean calls initially made a Pipe workflow fail. It was therefore restricted to the user Boolean command's regular Boolean path; the Pipe workflow passed after that change. Internal construction calls, direct unchecked kernel calls, empty results, and the disjoint-tool Difference fast path do not have this new result check. Native peak memory and representative large-model latency remain unmeasured. The product's separate non-rigid placement restriction also remains. Verification: 77 app controller tests passed; 114 Solid workflow tests passed with one ignored; 198 Solid integration tests passed with one ignored; 78 kernel tests passed with the original affine correctness reproducer ignored. Desktop was not rechecked.

### Consistent placement classification

The previous product placement gate used a 1e-10 orthogonality tolerance, while the native transform adapter requires OCCT's `gp_Trsf` to reproduce every matrix coefficient exactly before it uses the rigid path. Consequently a scale of `1 + 4e-11` passed the application gate but used the general affine transform; the expanded controller regression failed before the correction. A `1e-13` shear also passed the old tolerance. The adapter and product gate now share the exact same OCCT classification; the Rust caller validates the matrix before invoking it. Both small non-rigid fixtures are refused in Union and Boolean Two with document and Redo unchanged. The computed 45° Y-axis Union fixture succeeds with expected volume and Undo/Redo; kernel classifier checks computed 45° and 90° rotations and refuses the tested shear and scale. Some mathematically rigid floating-point matrices may fail the exact OCCT coefficient round-trip and are conservatively refused. This does not fix nonuniform-affine Boolean or protect already baked inputs.

Verification: app Solid controller 80 passed; kernel transform 13 passed; kernel Boolean 79 passed with the known affine reproducer ignored; Solid integration 198 passed/1 ignored and workflows 114 passed/1 ignored; the no-default-features fallback test passed. Desktop and native peak remain unverified.

### Disjoint-tool Difference follow-up

The new two-cutter kernel fixture uses the same baked nonuniformly scaled box as target, the centered sphere and a distant disjoint box as cutters, and the two output profiles 0.5 and 0.01 mm. The kernel path confirms disjoint cutters use the multi-tool path and requires either the analytic volume `256 - 18π` mm³ or refusal. The controller fixture saves and reopens the same arrangement, executes Boolean Difference, and verifies that both profiles are refused with `invalid BRep source shape` while the document and Redo remain unchanged. This refusal comes from the existing snapshot's `BRepCheck_Analyzer`, not the newer small-edge Boolean guard. The error wording does not distinguish an invalid result from an invalid input. This single failure fixture does not establish detection of all erroneous but structurally valid results, nor does it establish successful Difference for this geometry. No product behavior was changed in this follow-up. The controller suite passed 78 tests and the kernel suite passed 79 tests with the original affine Union reproducer ignored; the kernel suite includes the existing disjoint-tool and 21-cutter dice fixtures. Desktop and native memory remain untested.

Additional isolated kernel trials did not yield a shippable affine path. Reversing the Union operands still failed snapshot tessellation, as did applying scale and translation in two separate transformations. Applying the inverse affine to the sphere and performing Union against the unscaled box yielded a local volume 156.27433388979452 mm³ versus the analytic 156.27433388230813 mm³; transforming that result back to world space then failed with `transform produced an invalid shape`. Keeping a local result with placement would require product preview, publication and downstream-operation validation and would not alone repair already baked sources. The test was restored to its original ignored reproducer and the product guard was not relaxed. An [OCCT forum explanation](https://occt3d.com/dev/content/brepbuilderapigtransform-makes-boolean-operations-slow/) describes why GTransform uses B-splines to retain parameter ranges; it does not establish a remedy for this result or prove that parameter conversion is safe. Public source audit passed.

This is the OCCT check's result on this fixture, not a general exactness proof; it does not identify the cause of the bad Boolean. The diagnostic code was removed. The configured kernel Boolean suite again passed 75 tests with the known reproducer ignored; production transform source and the reproducer match the git objects above.

### Exact axis-permutation rotation control

The transform adapter now uses `BRepBuilderAPI_Transform` for proper signed-permutation matrices whose linear entries are exactly 0 or ±1 and determinant is +1, as well as the existing pure translations. It does not round near-rigid matrices to this category; other affine transforms retain the general path. In a temporary native diagnostic, the rotated-sphere control used an exact 90° Y-axis matrix and OCCT reported `GeomAbs_Sphere` for the transformed sphere; the scaled-box faces remained `GeomAbs_BSplineSurface`. Union still matched the analytic volume. Thus a spherical analytic representation with a changed orientation can pass this fixture, but the observation alone does not prove the root cause or justify a general seam repair. The temporary diagnostic was removed.

A separate native test checks that a cylindrical surface rotated by an exact signed-permutation matrix retains a usable analytic cylinder carrier, radius, volume and transformed bounds. ### Rigid matrices generated from trigonometry

A computed 90° rotation originally failed the cylindrical-carrier test even though the exact axis-permutation form passed. The transform adapter now considers proper near-orthonormal matrices as candidates for `gp_Trsf`, but uses that path only if OCCT's resulting scale is exactly 1 and all 12 coefficients compare exactly equal to the supplied matrix. OCCT documents that `SetValues` orthogonalizes, so a nonidentical result falls back to `gp_GTrsf`; the candidate tolerance alone is not permission to round. Computed 90° and 45° Y-axis cylinder fixtures retained a cylindrical carrier and correct radius/direction; the 90° carrier matched reference volume, while the 45° carrier deliberately encloses a larger extent because it is derived from the world AABB. A 1e-13 shear fixture remained on the general path, as shown by the analytic-cylinder carrier rejecting its resulting non-analytic surface. These tests do not establish all rotation matrices, general affine Booleans, desktop or native peak.

### Product-path applicability

The diagnostic input contains a box whose scale was already baked into its B-rep source and has identity document placement. The current controller separately rejects differently placed non-rigid inputs when it cannot establish the existing shared affine frame, before the kernel call. Therefore changing the checked kernel Union path alone would not support that separate placement case. The existing controller test boolean_union_baked_affine_source_is_correct_or_refused_without_losing_redo saves and reopens this kind of input, accepts either a validated result or safe refusal, and covers Undo/Redo when successful; a future functionality gate must explicitly require success for a suitable fixture instead of counting that disjunction as proof. Checked Union is also used to combine target and cutter groups for other Boolean commands; any kernel-level extension reaches those internal callers too and must be evaluated for them. This is a source audit, not a new runtime test or authorization to change behavior.
