# Shared resource payloads in retained-owner admission

The Undo inventory already recognizes shared immutable resource payloads, but coordinator aggregate retained-owner admission previously summed the full `Document::storage_usage` of every distinct historical document. A red/green fixture with one 4 MiB resource and two document versions sharing its immutable allocation measured 4,222,974 bytes before retaining history and 8,446,884 bytes afterward; the new assertion failed before the change. This is managed-byte accounting, not measured RSS.

For coordinator-owned document versions, admission now charges the same immutable resource payload allocation once across versions, while retaining document metadata and distinguishing separate allocations even if their bytes match. It uses a resource-identity index when a conservative bound for both temporary indexes is admitted; when the index cannot fit, the allocation-free comparison path is used. The test sets a budget only 1 MiB above retained usage, so the duplicate-inclusive fast bound cannot fit, and verifies that the fallback yields the same usage. Because document validation currently counts aliases within one document separately, the retained-owner total conservatively retains the largest per-document multiplicity of the same payload; this is not complete deduplication of such aliases.

The fixtures cover independent equal-content payloads, per-document aliases, actual Move transactions, Undo/Redo and the tight-budget path. A pre-existing `job_lifecycle` test expected historical snapshots to consume a single aggregate point quota. The project now explicitly applies point limits per document, so the fixture was changed to assert two staged one-point versions succeed while the public world stays unchanged; aggregate-byte refusal remains covered by `retained_peak_review` and resource transaction regressions. One first invocation accidentally used an unqualified `--exact` test name and ran zero tests; it is not counted as evidence. The correctly selected regression failed before the accounting change and passed afterward.

Windows E: default-feature development tests with `-j 2`: full `om9-core` test command succeeded, with two existing ignored benchmark tests and one existing unused-mut warning. The related resource, Undo, retained-peak and lifecycle tests passed. App gesture, Gumball and retained STL-capture tests were run separately; no desktop session was used. This initial revision did not deduplicate external retained captures; the follow-up below covers that case. It does not remove `Limits::default()`'s 256 MiB ceiling, implement the 60% aggregate RAM policy, deduplicate all geometry/cache owners, or measure behavior above 256 MiB. The allocation-free fallback and per-document repeated alias scan can cost more on long histories or resource-heavy documents; no release benchmark or desktop responsiveness claim has been made.

## External capture overlap

Two red/green fixtures exposed double charging of one shared 4 MiB resource payload: retained old capture versus current document reported 8,445,004 bytes rather than approximately 4 MiB, and two detached captured versions reported 8,472,662 bytes. Aggregate accounting now compares immutable payload allocation identity across internal retained owners and earlier live external captures, then charges only additional payload multiplicity while still charging document metadata. It uses allocation-free scans while holding the existing capture/reservation locks. Dead weak captures are ignored; physical RAM is not reserved by this accounting.

The fixtures pass after the change. Other tests verify equal-content but independently allocated payloads are both charged, that a shared payload survives coordinator replacement, and that dropping the last relevant capture releases its charge. The full `om9-core` test command passed on the E: default-feature development build with `-j 2`; two scaling benchmarks were ignored and an existing unused-mut warning remains. This checks resource `Arc` payloads only. Per-document repeated aliases are intentionally conservative; geometry buffers and other shared owners are not deduplicated here. `Limits::default()` remains 256 MiB, 60% admission is not connected, and no real >256 MiB or release performance measurement has been established. Many captures/resources may make the allocation-free scan expensive; measure before claiming UI responsiveness.

A further focused fixture confirms that when a captured document has two resource IDs aliasing one payload and the current document retains one, accounting conservatively preserves the larger per-document alias charge. The focused fixture passed separately after the full core run. Application regressions passed for two old STL capture/New/Open cases, the Surface snap worker's stale-receipt case, and nine gesture tests; these do not prove desktop presentation.
