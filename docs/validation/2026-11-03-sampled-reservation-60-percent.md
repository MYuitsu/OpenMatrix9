# Sampled external reservation: 60% ceiling

`TransactionCoordinator::reserve_external_memory` already accepted an optional `(total, available)` physical-memory sample, reserved `max(256 MiB, 10% total)` free headroom, and serialized outstanding reservation accounting. Before this change, that path did not use the sample's total RAM to cap the aggregate retained owners plus reservations at 60%; a red test with a 1 GiB total/available sample and a 1 GiB configured byte limit admitted 400 MiB plus 220 MiB of reservations, even though this exceeded 60% and both fit the separate available-headroom rule.

The initial implementation used the lower of the existing byte limit and `floor(total * 3 / 5)` when a physical sample was supplied, but did not retain that ceiling for later calls. Its existing per-document structural limits remained unchanged. The follow-up below closes the tested unsampled-reservation bypass, without claiming complete session admission.

The red/green test checks the two sequential simulated reservations, no mutation after refusal and release of the original guard. A two-thread simulated race verifies that only one of two 320 MiB reservations is admitted under a 1 GiB total sample and that both guards release. These are counter tests and intentionally do not allocate those amounts. The full `om9-core` test command passed before the final diagnostic-label adjustment, with two pre-existing ignored benchmark tests and an existing unused-mut warning; afterward all 21 focused retained-owner tests and the one selected STL worker capture test passed on the E: default-feature test build with `-j 2`. No UI session or native kernel workload was operated.

The interactive default still uses the 256 MiB limit. Document/Undo, GPU, native transients and all other operations are not yet consistently wired into a session-wide 60% account. The OS sample is not an OS reservation, may become stale as other processes allocate, and the conservative outstanding-reservation subtraction can double-count memory already materialized. Do not use this result as evidence that a real >256 MiB model works or that process RSS is capped. Continue separating document and operation structural limits from global owner/peak admission and obtain real-allocation release evidence before increasing the interactive ceiling.

## Retained sampled ceiling and held transaction data

A red/green test demonstrated that after accepting a reservation using a 1 GiB physical sample, a second reservation with no sample could previously take total reserved data above the learned 60% ceiling. The shared external account now retains the tightest ceiling learned from valid samples; later unsampled requests and retained-owner validation use it. A valid total-RAM sample tightens this capacity policy even if its request subsequently fails the free-RAM test, without reserving bytes or changing the document/history. Invalid samples do not establish a ceiling. Later larger samples do not relax a previously tighter ceiling in this account.

The capacity policy follows the shared account through coordinator replacement. If a replacement already has a tighter sampled ceiling than the old account, adoption explicitly refuses instead of discarding the tighter ceiling. This is conservative and may refuse replacement; a future complete session-owner design may combine such policies safely. Tests cover unsampled requests after releasing their guard, free-RAM refusal, a replacement account that would otherwise widen the cap, and a prepared transaction rejected after the ceiling tightens, preserving an actual Redo entry. A further red/green fixture shows held transaction/scene bytes must be subtracted from the learned cap before admission; the relevant held-usage, preparation, open and commit paths now start from the constrained limit snapshot.

On the E: default-feature development build with `-j 2`, 28 focused retained-owner tests and the full `om9-core` test command passed; two existing scaling benchmarks were ignored and an existing unused-mut warning remains. Application regressions passed for two retained STL capture cases across New/Open, one background STL worker case and nine gesture tests. These are simulated capacity counters and headless tests, not a real allocation above 256 MiB or a desktop test.

The policy is learned only once a caller supplies a valid physical sample; the normal interactive path does not yet establish it. An unsampled request does not check current free RAM. This slice does not inventory all scene/GPU/native/scratch allocations, does not eliminate the 256 MiB limit, and does not establish atomic coordination if another thread tightens the capacity policy between an operation's limit snapshot and its allocation/publication. Those races and full peak admission remain open. It is a conservative partial improvement, not a verified process or session RAM cap.
