# Hatch display mesh validation and memory accounting

`Geometry::Hatch` previously cloned its entire display mesh to invoke the `Geometry::Mesh` validator. The clone could allocate a second mesh before admission and had reduced Vec capacities, so it could undercount the original live buffers. The validator now borrows the existing mesh and uses the same mesh-geometry checks as `Geometry::Mesh`; it charges the original vertex, normal, color, face-vector and index capacities. A regression fixture with 4,096 vertex slots reported 716 bytes before the change versus the expected 98,948 bytes; after the change it agrees with direct mesh accounting and rejects a one-byte-short cap. A malformed face index remains rejected.

The subsequent UV and metadata follow-up unifies `Geometry::Mesh` validation with `Mesh::validate`, counts the allocated UV capacity even for an empty buffer, and uses checked arithmetic for UV corner counts. Invalid UV counts and non-finite UV values are now rejected consistently by `Geometry::Mesh`; previously that route omitted UV validation. Hatch accounting also includes the outer loop-vector and pattern string capacities. Red/green fixtures exposed missing charges of 16,384 bytes for UVs and 20,376 bytes for Hatch metadata; a separate document-level fixture verifies propagation into retained document usage. These are managed capacity counts, not process RSS measurements.

The full default-feature core suite passed on E: with `-j 2` and two pre-existing ignored benchmarks; six targeted Hatch/mesh tests and seven project codec tests passed. Other native and Rust owners, global 60% admission, the existing 256 MiB limit, and desktop behavior remain open. Scene and UI interaction checks are recorded in the live ledger.
