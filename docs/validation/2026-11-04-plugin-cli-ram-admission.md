# Plugin CLI document RAM admission, 2026-11-04

`--plugin-run-on` previously loaded its source directly with `Limits::default()` and `--plugin-run`/`--plugin-run-on` saved directly with the same 256 MiB default, without the Controller Open/Save reservations. Both commands now use the hardware-derived document limit; `--plugin-run-on` opens through the existing reserved batch Controller path, and both save using the Controller's existing Save reservation, including its scene usage. The shared save helper preserves the interactive guard, path capacity accounting and atomic archive save. CLI source names and extension-independent batch paths remain supported. Plugin execution still follows the existing transaction/plugin path.

On Windows, using default product features, external `E:/om9-surface-snap-validation`, `-j 2` and the existing built `build/sdk/hello-windows-x64.om9p`: a 2 MiB opaque-resource document was refused with `OM9_MAX_BYTES=1024` (clamped to 1 MiB), leaving source and an existing destination byte-for-byte unchanged. Retrying with 512 MiB succeeded; the input remained unchanged and the reopened result contained the plugin's SDK profile. This is a controlled small document with a real plugin, not evidence of a >256 MiB geometry file, native plugin peak, complete simultaneous owner coverage, or desktop behavior. The initial test used a smaller input and incorrectly expected the 1024-byte override to stay below the 1 MiB floor; it failed as a test assumption and was replaced with the 2 MiB payload.

Twenty `file_lifecycle` integration tests passed after the shared helper extraction (23.67 seconds build, 1.50 seconds tests). The plugin CLI test passed (1.24 seconds build, 1.75 seconds test). The existing `save_reserves_live_headroom_and_releases_it_on_success_or_failure` unit test also passed (27.02 seconds build, 0.02 seconds test). `migrate` still uses an independent default limit; not all plugin/native allocations or report serialization are admitted. Full P0 remains open.
