# Recorded change feed through SDK v1 — 2026-10-21

A plugin command can read the change batch recorded for the previous plugin command: real
revision range, cause `edit`, and one entry per added/removed/modified entity plus layer
entries. The feed is recorded at the plugin boundary from the committed before/after
documents, so it does not depend on the observer baseline. Owner: `OM9-L2-01-03`
(`OM9-L3-01-03-011`).

## Changed

| Layer | Change |
|---|---|
| Public SDK | `ChangeEntry`, `ProjectChange`, `Host::last_change`; `LastChange` request and capability. |
| Host | `PluginRun`/`Staged` carry the recorded batch the app attaches before the next command. |
| App | `run_plugin` snapshots the document before publishing and records `ChangeBatch::between(before, after, Edit)` after a successful command into one bounded controller field; the next plugin command receives it. |
| Example plugin | `ChangeDemo` returns the recorded batch. |
| Tests | Host test for the attached batch and the empty feed; native DLL test that `CreateProfile` records 3 `entity_added` entries with `to_revision > from_revision`, and that reading the feed stages no mutation. |

## Semantics fixed by this slice

- The feed holds **plugin commands only**: host commands outside the plugin boundary are not
  recorded (compare `document_info().revision` for those), so the contract never claims an
  incomplete history.
- Revisions are real: `from_revision`/`to_revision` come from the before/after documents.
- Entries are the change enum's kinds (`entity_added`, `entity_removed`, `entity_modified`,
  `layer_*`, `current_layer_changed`, `extension_changed`), each with the affected id when the
  variant names one.
- Reading the feed stages no mutation.
