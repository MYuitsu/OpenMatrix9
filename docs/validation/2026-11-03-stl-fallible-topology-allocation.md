# Fallible STL topology scratch allocations

The topology traversal builds temporary face/edge maps, per-vertex links, adjacency, a visited set and a pending stack. The export path and strict streaming writer now use `try_edge_topology_with_check`, which requests capacity with Rust's fallible reservation APIs before growing those structures. If a reservation reports failure, the export receives a budget error before its final destination is written. Cancellation still propagates while building and traversing topology. The existing infallible public topology wrapper remains for compatibility and can still panic on allocation failure; it is no longer used by these export paths.

Windows default-feature E: build with `-j 2`: 11 exchange STL unit tests passed, including cancellation and equivalence with the legacy result; seven STL policy tests passed; all 41 application STL integration tests passed together. `cargo check -p om9-app --no-default-features -j 2` passed with 17 existing warnings. No actual out-of-memory event or allocator failure was injected, so the failure mapping is based on code inspection and fallible API semantics, not a measured OOM test. Existing atomic-destination tests cover cancellation and other errors, not forced topology allocation failure.

This does not reserve the allocations against the planned 60% RAM budget or bound OCCT's native peak. Other export allocations can still be infallible, and OS overcommit or external memory pressure may kill a process without Rust receiving a reservation error. Per-insertion capacity checks were not benchmarked in release. The UI remains synchronous and background export remains gated on complete admission and lifecycle integration.
