## Shared before-state for change notifications

Undo, Redo, Builder application/history recomputation, Clear History and the plugin change feed now retain the coordinator's registered immutable document rather than deep-cloning the whole `Document` solely to compute a change batch. The retained allocation is shared and registered with the existing owner inventory until the local reference is released; it can still keep an old version alive and registration can refuse under pressure. This removes these specific redundant clones, not the independent copies needed by transaction preparation or all transient allocations. No before/after RSS or elapsed-time measurement was performed.

## 3DM native-process reservation

The 32 MiB refusal is explained by the current native-process policy, not by the point's geometry: the default cap is 128 MiB of native committed memory plus a conservative allowance for stdout/stderr buffering and pipe overhead, totaling **160.1875 MiB**. This is an admission reservation and child-process cap, not a measurement that a small import actually consumes 160 MiB. A generated one-point test now confirms the 32 MiB operation is refused with the specific `3DM native process reservation` budget reason and preserves the document. The policy was not silently lowered; choosing an adaptive cap would require measured safe operation and explicit behavior for large files.

3DM import now registers that native-process reservation as `Kernel` with the coordinator's shared account before snapshotting or launching the child. A physical-memory sample is used when available. The guard stays live through child completion and conversion, then releases on success or error; native tests verify the reservation is gone afterward. This brings the known child cap and bounded pipe allocations into shared admission. It does not reserve the entire source snapshot, conversion output, caller scene, allocator overhead or OCCT native scratch across all owners. The local snapshot still has its own aggregate limit checks, and no hard process-wide RSS or shared-GPU bound is claimed.

With the current rebuilt native adapter, 21 clipboard tests and six native roundtrip/pressure cases passed, including the 32 MiB error and reservation-release assertions; 41 exchange unit tests passed. The small and B-rep fixtures do not establish concurrent scheduling behavior, measured native peak, complete 3DM fidelity or desktop performance.

## 3DM source-snapshot admission

## 3DM import bundle handoff

After conversion, the known `ImportBundle` and receipt storage estimate is added to the shared reservation. Once the child has exited and the source snapshot is dropped, the reservation is atomically reduced to the retained bundle/receipt estimate. `PreparedNativeImport` carries that guard while waiting for transaction preparation; the prepared candidate document is registered in the shared owner registry before the guard is released. This is conservative while old and new owners coexist. The bundle estimate is computed after conversion has allocated it, and the transaction's private clone and metadata are not fully reserved before construction; receipt and other caller-held owners are not all visible to peers after the handoff. Consequently this is not an end-to-end 60% or RSS guarantee.

A real native-adapter test verifies that the prepared import retains a reduced nonzero shared reservation visible to a peer, then releases it on drop. Another verifies that the prepared candidate remains counted by a peer after the temporary guard is gone and ceases to be retained when dropped. These are controlled lifecycle tests, not proof of arbitrary concurrent schedules. Eight native 3DM, 21 clipboard and 42 exchange unit tests passed; 88 coordinator transaction tests passed, including atomic reservation shrinking. The fixtures do not certify large-file performance or geometry fidelity.

The current 3DM import policy also imposes an independent maximum source size of 64 MiB (`ImportOptions::max_file_bytes`), and the default native stdout limit is 16 MiB. These are separate from the interactive 256 MiB transition. They have not been removed or demonstrated appropriate for large user models; expanding them safely requires bounded streaming/worker admission, overflow checks and large real-file tests, rather than assuming that the 60% setting overrides them.

## Incremental JSON preflight reservation for 3DM

The external JSON structural preflight now accepts a monotonically increasing shared-admission callback without changing its existing external node, depth or duplicate-key rules. The 3DM importer grows its existing reservation during preflight before the estimated parser/key allocations and retains that estimate through typed inventory decoding. Requests grow in at least 1 MiB increments to avoid a shared-account lock for every JSON token; if the extra cushion does not fit, the code retries exactly the required increment. The final typed-inventory estimate can grow the reservation further. Input/output and some estimates overlap, so the result is conservative and can still refuse valid work under tight limits.

## 3DM size-limit audit and bounded pipe growth

The 64 MiB input limit exists both in the Rust import policy and the native adapter's archive checks; the native child also materializes an inventory JSON value and its serialized string, capped at 16 MiB. Parent pipe capture defaults to 16 MiB and native committed memory to 128 MiB. Export has separate 16 MiB request-packet and staged-output-file checks, while native archive inspection caps files at 64 MiB. B-rep payloads are additionally represented in JSON chunks, increasing transient storage. These are independent bounds; raising only one will not provide large-file import/export. The 16 MiB staged-file check applies to export validation and is not the same as stdout. Full streaming, memory admission and size/fidelity fixtures remain needed.

Windows native pipe capture previously requested exact capacity for every received chunk, which could repeatedly reallocate and copy as output grew. It now grows geometrically within the same logical output limit, uses fallible allocation and falls back to the exact required capacity if the larger request fails. A deterministic 65,536-byte, one-byte-at-a-time fixture observed no more than 17 capacity changes while preserving every byte and rejecting overflow; a real child emitted 8 MiB with verified content and was rejected cleanly at one byte below the limit. This validates scoped behavior, not a measured speedup or actual allocator peak. The changes do not increase any 3DM file, packet, process or stdout limit.

The Windows native-owner suite passed 29 unit tests with four clipboard-related tests ignored, plus nine process tests. All 21 clipboard and eight native 3DM tests passed with the current adapter. No large real 3DM, release timing, desktop or general geometry/topology acceptance is claimed.

## Scope and implementation

Interactive `MatrixApp::new` and `MatrixApp::from_file` now obtain their document byte limit from 60% of sampled total physical RAM instead of inheriting `Limits::default().max_bytes` at 256 MiB. The same application policy is used by `document_limits()` consumers; the Controller continues to use its shared non-widening managed ceiling. A lower `OM9_MAX_BYTES` override remains available, bounded by the hardware-derived ceiling. Unknown or zero physical capacity retains a conservative maximum of 256 MiB, and the UI reports the fallback in both status and transcript. Structural limits and `Limits::default()` were not globally raised; CLI paths that use that default retain their existing limits. The 256 MiB free-RAM reserve and the separate GPU fallback are unchanged.

New/Open carry the current Controller limits into replacement controllers. File readers retain checked byte, structure and reservation validation, but their effective interactive byte allowance now follows the session budget rather than the old fixed 256 MiB. This is a larger admission allowance, not removal of input validation. The setting is a managed-data ceiling and is not a process RSS or OCCT allocation bound. Physical-memory samples are point-in-time; unregistered owners, native scratch, allocator peaks and other operation paths remain incomplete.

## Mesh and surface incremental-scene preflight

`Scene::update_usage` formerly called the actual display mesh builders for mesh and NURBS-surface additions merely to estimate their usage, allocating and then discarding the display data before transaction admission. ## Continuous Undo and Redo scene reservation
