# One background STL worker per account

`StlExportJob::start` now acquires a Rust-owned atomic export permit from the capture's shared memory account after validating its reservation and target. A second background job using that account returns `Invalid("export already active")`; its reservation and capture drop normally and its destination is unchanged. The permit remains owned by the worker until work returns or panics. Dropping the job requests cancellation but does not release the permit while the native or other work is still running.

The permit account is transferred with external reservation/capture accounting on controller replacement. The new coordinator refuses an adoption over an already-active independent permit; failed adoption restores the original account. This supports a continuous per-account worker limit while old work drains, but **does not implement New/Open/close cancellation**. Ordinary synchronous STL export and the current UI path do not use this worker or permit, and the scope is one shared account, not a global process-wide policy.

Default-feature Windows build on E: with `-j 2`: 11 core retained-account tests passed, including competing permit requests and transfer across replacement. Six STL cancellation/worker unit tests passed, including a blocked worker whose job is dropped, permit retention until worker exit, and release after panic. Three STL background-job integration tests passed, including a busy request preserving an existing destination and releasing its reservation; two New/Open capture tests also confirm permit-account transfer. A `--no-default-features` check passed with 17 existing warnings.

This is a prerequisite, not completion of P0/P3b: reservation sizing remains caller-supplied and is not proved to cover the native mesher or other peaks; the interactive export remains synchronous; physical RAM admission, cancellation on lifecycle changes, UI busy/cancel feedback and desktop responsiveness remain open. The active OM9 session was not operated.
