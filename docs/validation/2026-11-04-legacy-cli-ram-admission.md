# Legacy CLI migration RAM admission, 2026-11-04

The explicit `--migrate-v1/v2/v3` commands previously used the independent 256 MiB `Limits::default()`. They now use the hardware-derived session limit and hold the existing shared-account CPU lease for available headroom (including the physical-memory sample and free-RAM reserve when available) while the legacy decoder, restored copy, verified archive replacement and report run. The archive's existing version checks, cancellation and atomic replacement are unchanged. Its internal logical accounting and this lease are not an RSS limit or proof of all allocator/native memory; the reservation is conservative and can refuse early. This is the existing explicit in-place migration to schema 4, not the future v4-to-v5 Save As workflow.

An integration fixture constructs a real schema-3 archive containing 100,000 cloud points. The 1 MiB minimum override refuses the conversion and the file remains byte-for-byte identical; retry at 512 MiB succeeds, schema 4 reopens, and the document ID, object ID, point count and final point are checked. The initial synthetic fixture incorrectly placed an opaque resource in legacy JSON without the required embedded payload section and was correctly rejected; the valid cloud fixture supersedes it. Six archive schema tests also passed, including cancellation, overflow and budget refusal preservation. E: debug target, default features, `-j 2`: integration build 1.33 s/test 3.20 s; archive build 3.27 s/tests 0.01 s.

This covers one schema-3 cloud fixture, not v1/v2 payload coverage, >256 MiB legacy archives, native operations, measured process peak, or desktop migration. Report/output errors after an already successful explicit in-place migration remain a separate diagnostic issue. The full managed-owner and v5 migration gates remain open.
