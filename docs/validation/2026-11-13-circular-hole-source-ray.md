# ExtractIsocurve: source-checked viewport face on a circular hole

The user approved testing a viewport-pick path that verifies the clicked point against the selected source face, while keeping the existing conservative behavior for selections without a captured viewport hit or for numeric inputs. A saved/reopened authored block with a radius-2 through-hole and 0.2 mm display deflection previously failed whole-display verification because ordinary triangle chords extend slightly across the curved trim.

The viewport face-pick path now retains the ray, camera, viewport, source and selection context for an editable root B-rep, using the existing NativeBrep infrastructure. The OCCT adapter resolves both the selected display-face witness and the ray intersection from the same source read; it rejects if they refer to different source faces, if the ray is ambiguous, or if no intersection is near the clicked display point. The Rust caller also checks the source hit against the captured viewport and revalidates the selection and scene for the pending command; extraction resolves the same witness/ray again against the immutable source. Existing point-free selected-face and numeric routes retain the whole-display verification. Rust owns session, source binding, admission and transaction; C++ is restricted to the necessary OCCT face resolution and clipping.

In the reopened circular-hole fixture, a simulated viewport face pick followed by CMD or menu-origin dispatch creates two curves in one Undo/Redo. A controller test independently checks the four endpoints against `[-5,-2,2,5]` along the center line at z=10 mm. A malformed small-hole display clicked inside its hole is refused with document and Redo preserved; changing the selected face after the command starts also refuses before commit. A box source test checks that a ray for the top face with a side-face witness is refused both at bounds lookup and extraction; non-finite combined witness tolerance is also refused. These checks are scoped to the tested geometries and events, not a proof for arbitrary corrupt displays, coincident or very close faces, all transforms or physical desktop. Native OCCT allocations and peak are not bounded by the Rust admission estimate.

The ExtractIsocurve suite passed 53 tests with 3 ignored; the three focused simulated viewport selection tests passed for editable box, native box and circular-hole block, with the circular case checking CMD and menu-origin dispatch. The 74 memory-recovery UI unit tests passed. A no-default-feature cargo check passed with existing warnings; it is not OCCT evidence. The debug application build succeeded. All builds used `L:/om9-target-surface` with `-j 2`; the running first-target executable was not replaced. Physical desktop for this change, runtime performance on large sources, real OOM and native peak remain unverified. The older `indexed_face_refinement_respects_a_trimmed_through_hole` test still directly invokes conservative whole-display verification without a stored hit and failed again in the final build; this change does not claim to fix that route.

## Scoped synchronous timing

One explicit debug diagnostic used the new editable B-rep viewport-ray path on a saved/reopened sphere with 30,016 display triangles. In that one process, selecting the face took 5.70 ms, starting ExtractIsocurve 3.87 ms and finishing it 229.05 ms; five curve samples matched the radius and Undo/Redo restored the complete document snapshots. This was a controller-level diagnostic on one machine and one sphere, not a desktop input measurement, controlled benchmark, worst-case bound or native peak. The route still performs source work synchronously; large or complex sources require separate evaluation if responsiveness becomes a problem.
